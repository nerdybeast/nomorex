# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

NoMoreX — a Flutter (mobile + web) strength-training log backed by Supabase. Users record personal bests (PRs), build workouts out of exercises, and program sets either as an absolute load or as a percentage of their 1-rep max.

## Commands

Every `flutter` command that runs or builds app code needs the Supabase config injected at compile time (see "Configuration" below), otherwise the app builds fine but silently cannot reach Supabase.

```bash
flutter run --dart-define-from-file=.env.json        # production Supabase
flutter run --dart-define-from-file=.env.local.json  # local `supabase start` stack

flutter analyze                    # lints (flutter_lints + custom_lint/riverpod_lint)
flutter test                       # full suite
flutter test test/workouts/set_editor_test.dart                  # one file
flutter test --plain-name 'add-exercise picker shows options'    # one test

dart run build_runner build --delete-conflicting-outputs   # regenerate *.g.dart
dart run build_runner watch --delete-conflicting-outputs
```

**Run `build_runner` before every commit that touches a file with a `part '*.g.dart';` directive, and commit the regenerated `*.g.dart` alongside it.** The generated files are committed, and they copy more than signatures: each provider's doc comment, and a hash of its body. So a comment edit or a change inside a provider's function body makes its `.g.dart` stale even though `flutter analyze` and the app are both fine. Only a signature, name or annotation change breaks analyze. CI's `checks` job runs `./scripts/check-generated.sh`, which regenerates everything and fails the PR on any difference. Run it yourself after committing and before opening a PR; it compares against git, so uncommitted generated files show up as differences. If it reports files you didn't touch, they went stale in an earlier commit; regenerate and commit them in their own `chore:` commit rather than reverting them. Use the script rather than a bare `build_runner build` to check: a plain build trusts its cache in `.dart_tool/build` and can skip a stale file, writing nothing, so the script runs `build_runner clean` first.

**Cloud sessions have no display, so run E2E under xvfb:** `xvfb-run -a ./scripts/e2e.sh linux` (`./scripts/verify.sh` already does this). Without it the desktop app can't open a window.

**Driving the web app in cloud sessions (headless Playwright):** `flutter build web --debug --dart-define-from-file=.env.local.json`, then `node scripts/web-shot.mjs <route> <out.png> [--flow scripts/web-flows/<flow>.mjs]`. It signs in as `a@a.com`, turns on Flutter's accessibility tree, runs the optional flow, and screenshots the route. **Drive flows with role locators**, e.g. `page.getByRole('button', { name: 'Add sets (%)' })`, `getByRole('switch', { name: 'Rep range' })`, `getByRole('button', { name: 'Increase Reps' })` (each `NumberStepperField` names its buttons `Decrease <label>` / `Increase <label>`). These find widgets by what they say rather than where they are, and every tap lands. Coordinate clicks (`page.mouse.click(x, y)`) still work as a fallback, but they drift with layout and occasionally drop taps on small targets like switches. A widget with no visible text or semantics label (a bare `IconButton`) has no name to find it by — give it a `tooltip` or `Semantics` label, which also fixes it for screen readers. **Don't put a separate button inside a `ListTile`/`CheckboxListTile`** (`trailing`/`secondary`): the tile merges its children into one semantics node, so the button is announced as part of the tile and can't be activated on its own. Widget tests won't notice, because they tap by position. Put it beside the tile in a `Row`, as `WorkoutDetailScreen`'s "Log RPE" does. `scripts/web-flows/add-pr.mjs` is an older, coordinate-driven example that writes a PR to the local stack.

**Visually testing the web app via claude-in-chrome:** `flutter run -d chrome --dart-define-from-file=.env.local.json --web-port=<PORT>` launches its own dedicated Chrome instance for Flutter's debug service — that instance is not the one claude-in-chrome controls. Run it in the background, then navigate a claude-in-chrome-controlled tab to `http://localhost:<PORT>` directly; it's a normal web server, so any browser tab can load the running app there. Requires the local Supabase stack up (`supabase start`) first.

Expect **rendering** to be verifiable this way and **tapping** not to be. Navigating straight to a route via the URL hash (`http://localhost:<PORT>/#/community/<id>`) reliably lands on any screen, and a signed-in session persists across reloads. But synthetic clicks land inconsistently on Flutter's canvas: large `FilledButton`s and the DOM-backed login inputs work, while list tiles and inline `WidgetSpan`-wrapped `InkWell`s can silently do nothing — no console error, no navigation — and dispatching `PointerEvent`s at `<flutter-view>` via the JS tool doesn't help either. Use the browser to confirm what a screen *looks* like, cover tap-driven behavior with widget tests, and after 2-3 failed clicks say plainly what's unverified rather than retrying.

Database (requires Docker + Supabase CLI):

```bash
supabase start
supabase migration new <name>   # never hand-name migration files
supabase db reset               # replay all migrations from scratch — do this before pushing
supabase db lint
supabase test db --local        # pgTAP tests in supabase/tests/database/
supabase status                 # prints local URL + publishable key for .env.local.json
```

AI edge function (Genkit; details in "AI / Genkit" below and `docs/build.md`):

```bash
supabase functions serve ai                         # local; needs supabase/functions/.env with ANTHROPIC_API_KEY
(cd supabase/functions/ai && deno task check)       # fmt + lint + type-check + unit tests, as CI runs it
```

**Never run `supabase db reset` (or any `--linked` variant of it) against the production/linked project.** It drops and recreates the database, which deletes real user data. `db reset` defaults to `--local` and that's the only form that should ever run in this repo or in CI. If asked to reset the linked/remote project, always stop and ask for explicit confirmation first, and be clear that it is a destructive action that can delete user data.

## Cloud sessions (Claude Code on the web)

The `SessionStart` hook sets up the CI toolchain and a local Supabase stack (see `docs/build.md`). Before calling a change done, run `./scripts/verify.sh` and report its summary as is. If a stage shows `SKIP`/`WARNING` (e.g. Docker unavailable), say that stage is unproven rather than implying it passed.

## Improving the development setup

Cloud or local, when something about the setup slows the work down or leaves a check unproven, suggest the fix: a missing tool, a flaky or slow step, a manual workaround you had to repeat. Examples are a tool `verify.sh` had to fall back for, or a script future sessions will need. Say what you'd change and why, and offer to add it to the current branch. Development improvements are welcome in feature work, as their own `chore:`/`ci:`/`docs:` commit so the feature commit stays reviewable. Don't make the change without asking, and mention it in the PR description.

Where a fix goes:
- **Cloud provisioning** lives in the repo, not in the environment's settings: `scripts/cloud-setup.sh` for slow installs (cached with the environment), `.claude/hooks/session-start.sh` for per-session steps and for filling in anything older cached setups lack, and `scripts/lib/cloud.sh` for shared helpers. Read tool versions from `pr-checks.yml` with `read_pins` rather than adding another pin. Change the environment itself (network hosts, variables) only when the repo can't do it.
- **Local development:** `scripts/` and `docs/build.md`. Prefer a script over a written-out sequence of commands.
- **Checks:** `scripts/verify.sh`, and `pr-checks.yml` when CI should run it too.

## Configuration

`lib/main.dart` reads `SUPABASE_URL` and `SUPABASE_PUBLISHABLE_KEY` via `String.fromEnvironment()`. These are **compile-time** constants, not runtime env vars — OS environment variables have no effect; the values must arrive via `--dart-define` / `--dart-define-from-file`. Unset values default to empty strings with no error. `.env.json` (prod) and `.env.local.json` (local stack) are gitignored and created per machine. Android emulators reach a local stack at `10.0.2.2`, not `127.0.0.1`. `SENTRY_DSN` works the same way. So do `SENTRY_ENVIRONMENT` (defaults to `development`), `SENTRY_RELEASE` and `SENTRY_DIST`, which only the deploy workflows pass: that's what keeps deployed Sentry events (`production`) apart from local ones. Full details in `docs/build.md`.

## Architecture

**Feature-first layout.** `lib/features/<feature>/{models,providers,screens,widgets,utils}`, with `lib/core/` (constants, theme, unit conversion, date formatting) and `lib/shared/widgets/` for cross-feature pieces. Features: `ai`, `auth`, `community`, `dashboard`, `exercises`, `personal_bests`, `profile`, `shell`, `workouts`, `programs`.

**No repository/service layer.** Riverpod notifiers talk to `Supabase.instance.client` directly, and mutations end with `ref.invalidateSelf(); await future;` so callers can `await` a completed refetch. Follow that shape rather than introducing a data-access abstraction.

**`invalidateSelf()` is rarely enough — several keepAlive providers cache the same rows.** `workoutsProvider`, `archivedWorkoutsProvider`, `inProgressWorkoutsProvider`, `finishedWorkoutsProvider` and `communityWorkoutsProvider` all run their own `select('*, workout_exercises(*, exercises(name))')`, so a workout's exercises are cached in as many places as there are lists showing it. A mutation must invalidate every provider whose *rendered output* changes, not just the one it was called on: `WorkoutDetailNotifier.addExercise`/`removeExercise` invalidate `workoutsProvider` because the Workouts list renders `w.exercises.length`, and `PersonalBestsNotifier.addPr` invalidates both `oneRepMaxProvider` and `oneRepMaxByNameProvider`. Skipping this doesn't fail loudly — the stale value just sits there until some unrelated mutation happens to refetch, which is why "it's wrong until I refresh the page" bugs in this codebase are almost always a missing cross-provider `ref.invalidate`.

**Reading an async provider inside a callback: `await ref.read(p.future)`, not `ref.read(p).asData?.value`.** These providers are `keepAlive` but still lazy, so if nothing in the current screen `watch`es one, `.asData` is `null` at the moment a tap handler runs — indistinguishable from a legitimately empty result. `SetPrLink` (`lib/shared/widgets/set_pr_link.dart`) awaits the future for exactly this reason: treating "not loaded yet" as "the user doesn't have this exercise" would silently create a duplicate.

**Auth-scoped providers.** Every provider that reads user data is `@Riverpod(keepAlive: true)` and starts with `ref.watch(authStateProvider)` before reading `currentUser?.id`, returning empty when null. `authStateProvider` wraps `onAuthStateChange`. Omitting that watch leaks the previous user's data across a sign-out — keep it in any new data provider.

**Models are hand-written.** Plain immutable classes with a `fromJson` factory; no freezed or json_serializable. Nested Supabase selects (`select('*, workout_exercises(*, exercises(name))')`) are unpacked inside the parent's `fromJson`, which also sorts children by `position`. Match that pattern when adding a model.

**Routing** lives entirely in `lib/app.dart`. `RouterNotifier` listens to `authStateProvider` and redirects: unauthenticated users off any non-public route to `/`, authenticated users off `/` and `/login` to `/shell/home`. The shell tabs are a `StatefulShellRoute.indexedStack`; detail/edit/create routes sit outside the shell. All paths are constants in `lib/core/constants/app_constants.dart` — add new ones there, not as string literals.

**Theme: Sleek Orange v3, light and dark.** `AppTheme.light()` / `AppTheme.dark()` (`lib/core/theme/app_theme.dart`) build both themes from one set of component rules and two `NomorexPalette`s; `app.dart` follows the device setting (`ThemeMode.system`). The design system itself (tokens, components, usage rules) is the "Sleek Orange Design System" artifact; token names in `NomorexPalette`/`NomorexTokens` match it one to one. **One accent, so `ColorScheme.secondary` is a trap:** `secondary`/`tertiary` and every `*Container` role are pinned to the orange (or its subtle wash) so stock M3 widgets don't fall back to Material's baseline purple/teal — reaching for `colorScheme.secondary` to get "the other color" silently gets you orange. `colorScheme.error` is the danger *text* color (validation and failure messages); destructive button fills come from `NomorexTokens.dangerButtonStyle`. Anything without a stock slot lives on the `NomorexTokens` extension — read it with `NomorexTokens.of(context)`, which falls back to the same stock tokens in widget tests that build a bare `MaterialApp`. Inter and JetBrains Mono are bundled under `assets/fonts/` and declared in `pubspec.yaml` (licenses registered in `main.dart`); don't reintroduce runtime font fetching such as `google_fonts`, which leaves text in the system font offline and contacts Google on every install. The blue is `NomorexTokens.info` (text only, never a button); the neutral equal-weight button is `secondaryButtonStyle`; weights render in the mono `weight`/`weightMd`/`weightLg` styles; mono caps section labels use `eyebrow`. Related rows go in one bordered `ListGroup` (`lib/shared/widgets/list_group.dart`) rather than a card each — row widgets built on `GroupableTile` drop their card chrome automatically inside one. Add new design tokens there rather than hardcoding a `Color` at the call site.

**Responsive shell.** `AppShell` renders a `BottomAppBar` + centered FAB below 600px and a `NavigationRail` above it (`isMobile()` in `lib/shared/widgets/responsive_layout.dart`). Because the shell always renders its own FAB, **any FAB on a screen inside the shell must set an explicit `heroTag`** — the default sentinel collides during route transitions and can crash the framework. `test/workouts/fab_hero_tag_test.dart` and `test/programs/fab_hero_tag_test.dart` guard this. There are 5 shell tabs (Home, Programs, Workouts, My PRs, Community) — a 5th tab means updating both `AppShell`'s mobile icon `Row` and desktop `NavigationRail` destinations by hand, since there's no loop over a route config.

**Programs are authoring-time templates; Workouts stay the only runtime/logged entity — but a program run is tracked.** A `Program` is a reusable template (`programs -> program_weeks -> program_days -> program_exercises -> program_sets`, mirroring the `workouts -> workout_exercises -> workout_sets` shape one level deeper, minus logging fields). "Starting" a program calls the `start_program` RPC, which inserts a `program_instances` row and bulk-materializes the template into ordinary `workouts`/`workout_exercises`/`workout_sets` rows stamped with `program_instance_id`/`program_day_id` (see Database below) — logging itself is still just a normal workout through the existing screens. On top of that, the instance is surfaced back to the user: the dashboard's "Current Programs" section and `ProgramInstanceDetailScreen` (`lib/features/programs/screens/`) read active `program_instances` to show upcoming/in-progress status and highlight today's day (`isProgramDayToday` in `utils/program_progress.dart`), and `WorkoutsNotifier`'s query excludes any workout with a non-null `program_instance_id` so materialized workouts don't flood the general Workouts list — they're reachable only through the instance screen, whose day cards push straight to the real `WorkoutDetailScreen`. `SetEditor` (`lib/features/workouts/widgets/set_editor.dart`) is shared between editing a workout and authoring a program via the `EditableSetRow` DTO (`lib/shared/models/editable_set_row.dart`); `WorkoutSet.toEditableRow()` / `ProgramSet.toEditableRow()` map into it.

**AI / Genkit: one edge function, `supabase/functions/ai`, Genkit JS + `@genkit-ai/anthropic`, served through `@genkit-ai/fetch`.** The Anthropic key is a function secret and never ships in the app. TypeScript rather than Genkit Dart because Supabase Edge Functions only run Deno. Each flow is `flows/<name>.ts` exporting `define<Name>(ai, model)`, registered in `flows/mod.ts`, and served at `POST /functions/v1/ai/<flowName>` with body `{"data": …}`. The client calls it with `callGenkitFlow()` (`lib/features/ai/utils/genkit_call.dart`), which goes through `functions.invoke` (session JWT attached automatically) and turns every failure into a `GenkitFlowException`. Rules that fail quietly if broken:
- **Data access goes only through the caller's RLS-scoped client.** `supabaseAuth` (`auth.ts`) verifies the JWT and puts `{auth: {uid}, supabase}` on the flow context. Every flow starts with `requireUserContext(context)`, and every flow in `mod.ts` is wrapped with `withActionOptions(…, {contextProvider: auth})`. **Never create a service-role/secret-key client there.** It would bypass RLS, and a prompt-injection bug would become a cross-user data leak.
- **Wrap every `ai.generate` in `callModel()` (`genkit.ts`).** Without it, a bad Anthropic key surfaces as `UNAUTHENTICATED`/401 with the provider's raw error. The app can't tell that apart from an expired session, and the message leaks upstream details. `callModel` logs the real error server-side and returns `UNAVAILABLE`, so 401 only ever means the user's session.
- **Don't rely on Zod `.default()` in flow input.** The HTTP handler doesn't apply schema defaults: `{"data":{}}` arrives with the field `undefined`.
- Import `retry` from `genkit/model/middleware`. `genkit/middleware` has types but isn't in the package's `exports`, so the worker fails to boot. Cap `maxDelayMs` so retries can't outlast the function's wall-clock limit.
- Pick models by tier (`MODELS` / `modelFor()` in `genkit.ts`), not raw IDs. The plugin resolves IDs it doesn't know by name, so a newer model needs no plugin bump.
- Context providers run only on the HTTP path. A flow started from the Genkit Dev UI's Run button has no user and fails `UNAUTHENTICATED` by design. Get traces by driving `dev.ts` over HTTP under `genkit start`.
- `.github/workflows/deploy-functions.yml` deploys the function with `verify_jwt` on. **Don't add `[functions.ai]` to `supabase/config.toml`:** the GitHub integration deploys anything declared there, bundles it server-side (5 MB limit), and fails with a 413. The CLI's Docker bundling allows 20 MB and the function is about 18.7 MB, so check the size before adding npm dependencies. Deno is pinned to 2.1.4 in `pr-checks.yml` and `verify.sh` to match the edge runtime, so bump them together.
- **`startAiImport` runs in the background and reads the model's reply as plain text on purpose.** It returns a job ID and finishes in `EdgeRuntime.waitUntil`; the job row is the only outcome the app sees. The model doesn't reliably follow a schema (`constrained: true` still returned out-of-enum values and code fences), so `ai_import/normalize.ts` parses the text and moves any bad value into a note or `unstructured` rather than failing the import. Change the output format in `ai_import/prompt.ts` and `normalize.ts` together, and re-measure a 10-page file afterwards: output sits near the 20,000-token cap (17,649 on the dense synthetic test), and extra per-exercise fields can push it over. File type and size are checked from the bytes in `ai_import/file_check.ts` before any model call.
- **`supabase/functions/ai-import-cleanup` is the one function allowed a service-role key**, and it holds no AI code, so the `ai` function, which reads untrusted files, never gets one. It runs `ai_import_sweep()` (service_role only) and then deletes the returned upload folders through the Storage API. Deleting `storage.objects` rows in SQL leaves the stored files behind. It's declared in `config.toml` with `verify_jwt = false`, because its only caller sends the `AI_IMPORT_CLEANUP_SECRET` function secret rather than a session. It checks that secret itself and answers 503 while the secret is unset. A folder it fails to empty comes back from the next sweep, and that's the retry. The app deletes an import's files itself on accept or discard (`AiImportJobsNotifier.removeImportFiles`), so the sweep only catches what that missed, plus abandoned and orphaned uploads after 7 days.
- Tests: `deno test` with a fake model (`ai.defineModel`) and a fake Supabase client, no network. Flutter tests override the notifier's `callFlow()`. The debug-only Profile → "Test AI connection" button (`AiSmokeTestNotifier`, `smokeTest` flow) is the end-to-end check. `functions.invoke` doesn't consume SSE, so a streaming flow would need `package:genkit/client.dart`'s `defineRemoteAction` instead. **Any new user-facing AI feature needs a per-user cap like imports' (`ai_import_check()` counted on the server) before it ships;** the Anthropic account's spend limit is only a backstop.

## Domain rules

- **Weights are stored in kg everywhere** (`weight_kg`, `absolute_weight_kg`, `actual_weight_kg`). Convert only at the display/input boundary using `lib/core/utils/weight_converter.dart` and the user's `unitPreferenceProvider` (from `profiles.unit_preference`, defaults to `'kg'`).
- **Sets have three weight modes.** `weight_mode = 'absolute'` uses `absolute_weight_kg`; `'percentage'` uses `percentage` against the lifter's 1RM; `'open'` prescribes no load at all (both columns null), so the lifter picks the weight on the day, as for "Vert Pull 3×7–9, %1RM NA" or bodyweight work. `resolveSetWeightKg()` in `features/workouts/utils/set_resolver.dart` is the single place that resolves this, and returns `null` both when a percentage set has no 1RM to resolve against and for every open set — screens must handle that null rather than defaulting to zero, and must check `isOpenLoad()` first: an open set shows `kOpenLoadLabel` ("choose load"), never "0 kg" and never the `SetPrLink` shortcut, because there's nothing to resolve. Open sets are added from the weight dialog's "No set load" switch (`AbsoluteSetBatch.weightKg == null`). They're the one kind with a "Log weight" button on a live session (`WorkoutDetailNotifier.logWeight`), which writes logging-only `actual_weight_kg`, never copied, like `actual_rpe`. A percentage set can also prescribe a **%1RM range** (`percentage_max`, e.g. 67–72.5%): screens that show a resolved weight use `resolveSetWeightRangeKg()` (same null rule, plus a `high` end resolved from the same 1RM) and render it with `formatResolvedWeightRange()`, so the ` (est.)` marker covers the whole range. Show a percentage with `formatPercentTarget()` (`core/utils/percent_range.dart`), never `toStringAsFixed(0)`, which turns 72.5% into "73%".
- **A percentage set's 1RM basis defaults to its own exercise, but can be a different one.** `workout_sets.basis_exercise_id` / `program_sets.basis_exercise_id` (nullable FK to `exercises`) let a set be programmed as e.g. "Front Squat @ 75% of Clean & Jerk". `resolveBasisExerciseId(set, exercise)` in `features/workouts/utils/set_resolver.dart` returns `set.basisExerciseId ?? exercise.exerciseId` — always look up `oneRepMaxProvider` by that, not by the set's own exercise id. The basis picker in `SetEditor`'s "Add sets (%)" dialog is unrestricted (any exercise in the catalog, not just ones already in the workout/program).
- **1RM is derived, not stored — and may be estimated.** `oneRepMaxProvider` maps `exerciseId -> OneRepMax` (`lib/shared/models/one_rep_max.dart`), taken from the user's *latest* `personal_bests` entry for the lift (by `date`, then `created_at`) whatever its rep count — the same entry the My PRs card shows as current, so a newer, lighter PR replaces an older, heavier one. A single is used as-is; a multi-rep entry is estimated. `OneRepMax.isEstimated` records which, and **every surface that renders a weight resolved from a 1RM must carry that flag through** — `formatResolvedWeight()` (`core/utils/weight_converter.dart`) appends the ` (est.)` marker, so use it rather than `formatWeightForPreference` for a resolved percentage weight. Estimation uses the user's `profiles.one_rep_max_formula` (Brzycki/Epley/Lander, default Brzycki) via `estimateOneRepMaxKg()` in `core/utils/one_rep_max_formula.dart`, and is withheld entirely outside 2..`kMaxEstimableReps` (10) reps — such an entry is skipped so the next most recent usable one wins, and a lift with only high-rep PRs is simply absent from the map, the same "no 1RM" state as having none. Both 1RM providers `ref.watch(oneRepMaxFormulaProvider)`, so changing the setting recomputes them; don't add a manual invalidation. Personal bests remain the source of truth for programming percentages. The **all-time best** that PR history shows is a different thing: the entry with the highest estimated 1RM under the same formula (`allTimeBest()` in `features/personal_bests/utils/all_time_best.dart`, earliest wins a tie, unestimable entries skipped). It's display-only — percentages still resolve from the latest entry, not the all-time best.
- **An `exercises.id` only means something inside one user's catalog — across users, match on name.** Two users who both have a custom "dude pulls" have two unrelated rows with different ids (there's no unique constraint on `name`, so duplicates by name are expected, not a data error). This matters everywhere a viewer looks at someone else's data: a public workout's `workout_sets.basis_exercise_id` points at the *owner's* exercise, while the viewer's PR for the same lift hangs off *their* id, so an id-keyed lookup silently misses forever. Resolve a viewer-facing 1RM through `lookupOneRepMax()` (`features/workouts/utils/set_resolver.dart`), which tries `oneRepMaxProvider` by id and then falls back to `oneRepMaxByNameProvider` by lowercased name; when a viewer needs their *own* row for a foreign exercise, go through `ExercisesNotifier.ensureExerciseByName()`, which find-or-creates by name. The two halves must agree on name matching or a user can record a PR that never resolves anything.
- **Percentage sets on another user's workout resolve against the *viewer's* 1RM.** `CommunityWorkoutDetailScreen` is a preview of "what would this session cost me", not a transcript of what it cost its author — the resolved weight renders in `NomorexTokens.info` (blue), absolute-weight sets stay default-colored because they're the same load for everyone, and a set with no resolvable 1RM offers the `SetPrLink` shortcut instead. `WorkoutDetailScreen` also renders other users' public workouts and follows the same rules.
- **Adding sets uses stepper inputs, not free text.** `SetEditor` (`lib/features/workouts/widgets/set_editor.dart`) uses the shared `NumberStepperField` (`lib/shared/widgets/number_stepper_field.dart`, tap +/- or type directly, floored at a sensible minimum) for sets/reps/percentage/weight — there's no shorthand grammar to parse. The percentage dialog has a single %1RM stepper shared by every set in the batch, like the weight dialog, so it stays a fixed height — wave-loading (a different percentage per set) means adding another batch. Reps and %1RM each have an optional range switch ("Rep range", "%1RM range") that reveals a Max stepper, built from the shared `_RangeInput`; a range narrowed to one number is saved as a single value (the `*_max` column stays null). `ParsedSet` (`lib/features/workouts/utils/parsed_set.dart`) is the reps+percentage DTO (with optional range tops) passed to `WorkoutDetailNotifier.addPercentageSets`. The weight dialog collects sets/reps/weight together and calls `addAbsoluteSets`, converting from the display unit to kg first.
- **RPE is a target on the set and, separately, a logged result.** `rpe_min`/`rpe_max` (1–10, half steps; `rpe_max` null = a single RPE) are prescription columns on both `workout_sets` and `program_sets`, set from the "Target RPE" switch in both `SetEditor` dialogs and shown as "RPE 6–7" via `formatRpeTarget()` (`core/utils/rpe.dart`). `workout_sets.actual_rpe` is logging-only, like `actual_reps`: written by `WorkoutDetailNotifier.logRpe` from the "Log RPE" button on a live (`in_progress`/`paused`) session, shown read-only afterwards, never pre-filled from the target, and never copied by `copiedSetRow`/`copy_workout`.
- **The privacy policy is `web/privacy.html`.** It's a static page that the web build copies through, published on GitHub Pages at `AppConstants.privacyPolicyUrl`, which Profile's "Privacy policy" link opens through `externalLinkOpenerProvider` (`core/utils/external_link.dart`). The same URL is entered in App Store Connect and Play Console, so it mustn't move. Its `#delete-account` section is the account-deletion page Google Play requires. **A change to what the app collects, shows to other users or sends to a third party** (a new personal-data column, the Sentry user context in `sentryUserSync`, a new service provider, the AI import notice) **updates the policy, `ios/Runner/PrivacyInfo.xcprivacy` and the store data-disclosure answers in the same PR.** `test/privacy_policy_test.dart` fails while any `class="todo"` placeholder is left in it.
- **Exercises are shared or custom.** Rows with `is_predefined = true` are visible to everyone; custom ones are scoped by `user_id`. The list query is `.or('is_predefined.eq.true,user_id.eq.$userId')`.
- **Predefined exercises aren't managed by migrations.** They live in `supabase/seed.sql`, which only ever runs against local/CI stacks via `supabase db reset` — production's actual predefined rows were inserted manually and are not tracked in this repo. It's fine if `seed.sql` drifts from what's in production; it exists to give local dev and CI a representative list, not to be the source of truth.
- **Tempo/pause/technique modifiers aren't separate exercises.** "Pause Front Squat," "Tempo Snatch Deadlift," etc. all log against the base lift (e.g. "Front Squat") with the modifier captured as a note on the `workout_exercise`/`program_exercise` row — this keeps 1RM/PB tracking coherent. A modifier only earns its own `exercises` row when a competent lifter would track a separate PR for it (e.g. Hang Power Clean vs. Power Clean).
- **Programs have no hard delete.** "Delete" in the UI archives (`programs.is_archived = true`, reversible via restore) rather than issuing a real `DELETE` — `program_instances.program_id` uses `ON DELETE RESTRICT` as a database-level backstop, but the app itself never exposes hard delete once a program has instance history.
- **Workouts archive; hard delete only from the archive.** Archiving sets `workouts.is_archived`/`archived_at` (`20261027023100_archive_workouts.sql`) and is reversible. `WorkoutsNotifier.archiveWorkout`/`restoreWorkout`/`deleteWorkoutPermanently` act on the **whole `workout_group_id`**, not one row, because one Workouts-list card stands for every session of a workout. Acting on just the representative would bring a sibling session up in its place. `deleteWorkoutPermanently` also filters on `is_archived = true`, so an active workout can't be hard-deleted even by a bug in the UI. It's only offered from the Workouts screen's Archived tab (`ArchivedRowActions`'s "Delete permanently"). Archive is hidden for a live (`in_progress`/`paused`) session and for program-materialized workouts (`canArchiveWorkout`). An archived workout leaves the Workouts list, Community (`copy_workout` raises `archived:`) and the copy-count hint, but **its finished sessions stay in history**: `finishedWorkoutsProvider` deliberately doesn't filter on it. Archived programs and workouts open read-only (no edit/start/repeat, just Restore). Repeating an archived session would add a live row to an archived group. Both list screens use `ActiveArchivedTabs`, and archived rows use `SummaryCard(archived: true)`, as specified in the design system.
- **Community content is copied, never shared live.** Saving or starting another user's public workout/program calls `copy_workout` / `copy_program` (`20261013023308_add_content_copies.sql`), which build a private copy owned by the viewer in one transaction — exercises mapped into the viewer's catalog by name via `map_exercise_for_viewer`, logged results never copied, and for Start the copy is then run through the existing `start_workout_session` / `start_program`. A copy is marked `is_copy` **permanently** (a `BEFORE UPDATE` trigger rejects un-marking it) and can never be public (`CHECK (not (is_copy and is_public))`), so the Public switch is disabled on copies. Copy status must follow anything derived from a copy: `start_program` stamps it onto materialized workouts, and every client path that creates a workout from an existing one (`duplicateWorkout`, the next instance in `finishWorkout`, `repeatWorkout`) spreads `copyAttributionColumns()` (`features/workouts/utils/workout_copier.dart`) into its insert — **a new such path must do the same**, or duplicating becomes a way to re-publish someone else's work. The author's name is a snapshot (`copied_from_display_name`) because `profiles_select` hides an author's profile once they stop sharing; render it through `CopiedFromBadge` / `copyAttributionLabel()`.

## Database

Schema is code under `supabase/migrations/`. Tables: `profiles`, `exercises`, `personal_bests`, `workouts`, `workout_exercises`, `workout_sets`, `programs`, `program_weeks`, `program_days`, `program_exercises`, `program_sets`, `program_instances`, and `ai_import_jobs`, `ai_import_results`, `ai_import_limits`, `ai_import_consents`. `workout_exercises`, `workout_sets`, and all `program_*` tables carry a denormalized `user_id` so RLS can be enforced without joins — new inserts must populate it.

**AI import tables are written only through functions.** Users have `SELECT` on their own `ai_import_jobs`/`ai_import_results` and no direct writes, so they can't edit the rows that enforce their own quota. `ai_import_start`, `_finish`, `_claim`, `_mark_accepted` and `_discard` are the project's `SECURITY DEFINER` exception (justified on #79); each does one transition on the caller's own job, and anything new like them needs the same care: `search_path = ''`, an explicit `auth.uid()` ownership check, and `anon` revoked, since default privileges grant it every routine. One `ai_import_jobs` row is one AI run, so a re-run adds a row and marks the old one `replaced`; never delete rows to tidy up, because the caps count them. Whether a failure counts is decided inside `ai_import_finish` from its code, not by the caller. Limits and the off switch are the single row in `ai_import_limits`. It ships with `enabled = false`; `seed.sql` turns it on for local and CI stacks. `ai_import_accept` saves a reviewed import in one transaction, `SECURITY INVOKER` apart from the claim and mark-accepted helpers. Its payload is the stored result with each absolute load as `weightKg`, converted by the client; a raw `weight` is refused by the set constraint rather than saved in the wrong unit. Imports are `is_copy = true` for privacy, plus `is_imported` for the "Imported" label, so anything that derives a workout must carry both (`start_program`, `copyAttributionColumns()`). Files live in the private `ai-imports` bucket at `{user_id}/{import_id}/{file}`, and its upload policy also requires the notice to be accepted and `ai_import_check()` to allow a start. The app side is `AiImportIntakeNotifier` (`lib/features/ai/providers/ai_import_intake_provider.dart`): it refuses files over the limits before upload (one PDF or up to `max_images` images, never a mix), uploads them as `page-N.<ext>` because the flow reads files in natural name order, then calls `startAiImport`. Any failure before the start deletes what was uploaded; a start whose outcome is unknown (`NETWORK`/`UNKNOWN`) leaves the files, since the import may be reading them. `prepareImportImage` downscales to 2576 px on the long edge (Claude's limit), turns photos upright and strips EXIF so a photo's location is never uploaded. The picker does most of that on iOS, Android and web; the Dart fallback covers desktop. Its client checks are only for the user's benefit, so a new rule that matters must also be enforced on the server. The way in is `AiImportButton`, an app-bar action on Workouts and Programs. It's hidden while `ai_import_limits.enabled` is false, so **the off switch is `update public.ai_import_limits set enabled = false;`** (and `true` to turn it back on). That both hides the entry points (on the next launch or resume) and makes the server refuse every start; an import already running still finishes. The import screen checks `ai_import_check()` as it opens (`aiImportGateProvider`). `consent_required` shows the one-time notice, which names Anthropic and, when accepted, inserts the user's `ai_import_consents` row; "Not now" leaves without recording or uploading anything. Any other refusal (switched off, an import already running, a cap reached) shows `importCheckMessage()` instead of the file pickers. Change the notice's wording together with the privacy policy (`web/privacy.html`) and the store data-disclosure answers, which describe the same thing. Job status reaches the app through `aiImportJobsProvider` (`ai_import_jobs_provider.dart`), the only source of truth: Realtime and app resume only prompt a re-read, because events missed while disconnected aren't replayed. `aiImportJobWatchProvider` subscribes to Realtime **only while a job is processing** (and re-reads on every (re)subscribe), so users who never import never hold a socket open; a job started on another device while this one is open shows up on the next resume or Home refresh. A job still `processing` past `max_job_seconds` is shown as failed (`AiImportJob.state`) without waiting for the sweep. `AiImportJobAlerts`, wrapped around the app in `MaterialApp.router`'s `builder`, re-reads on resume and shows one floating snackbar per job that finishes (`ImportAlertTracker`: jobs already finished at launch are the baseline and don't alert). It sits above the `Router`, so it navigates through a callback rather than `context.push`. Anything that changes a job's status from the app (accept, discard, start) must `ref.invalidate(aiImportJobsProvider)`. The review (`AiImportReviewScreen`, `/ai-import/review/:jobId`) never edits the stored result in place: it parses it for display (`AiImportResult`) and applies the user's fixes to a copy with `buildReviewedPayload()` (`models/ai_import_result.dart`) when they accept. That's where each absolute load becomes `weightKg`, in its printed unit or else the kg/lb the user chose, and where an exercise fix is applied to every exercise and basis lift of that name. A custom exercise chosen in review isn't created until accept, so a discarded import leaves none behind. Re-run as the other type calls `startAiImport` again with the same `import_id`, which needs the uploaded files still in place.

Any new table in `public` **must** enable RLS and add ownership policies `TO authenticated using ((select auth.uid()) = user_id)`, with UPDATE declaring both `USING` and `WITH CHECK`. `supabase db lint` runs in CI.

**Database tests are pgTAP files in `supabase/tests/database/*.test.sql`**, run by `supabase test db --local` (in `verify.sh` and CI's `db-validate`, after a reset, so the seeded users exist). They're the only tests that exercise the server-side functions and constraints. Widget tests never reach the database. `set_prescription_copies.test.sql` is the pattern: insert fixtures as superuser, then `set local role authenticated` plus a `request.jwt.claims` sub to act as a seeded user, and wrap everything in `begin … rollback`. **Any change to `start_program`, `copy_program`, `copy_workout` or a `workout_sets`/`program_sets` constraint should add or update a test there.** `.claude/settings.json` denies `--linked`/`--db-url` on every `supabase` command, so these can't be pointed at production by accident.

**Programs schema.** `programs -> program_weeks -> program_days -> program_exercises -> program_sets` mirrors `workouts -> workout_exercises -> workout_sets` one level deeper (`program_sets` has no `completed`/`actual_*` columns — those stay logging-only on `workout_sets`). `program_days.position` is the day's *global* order across the whole program (not just its week) and drives both drag-reorder and start-date materialization math; `day_number` is display-only and intentionally not unique per week, since two sessions (e.g. AM/PM) can share it. `workouts.program_instance_id` / `workouts.program_day_id` (both nullable, `ON DELETE SET NULL`) link a materialized workout back to the program run that generated it, without making logged history depend on the template surviving.

**`start_program(p_program_id, p_start_date)`** (in `20260805020858_create_start_program_function.sql`) is the first non-trivial server-side `plpgsql` function in this codebase beyond the existing trigger functions (`handle_new_user`, `set_updated_at`). It's `SECURITY INVOKER` (not `DEFINER`) so it stays gated by the same RLS a direct client insert would hit, and does the whole weeks→days→exercises→sets walk in one transaction — this is why "Start Program" is an RPC call rather than a client-side loop like `WorkoutsNotifier.duplicateWorkout()`: a multi-week program is large enough (dozens of workouts, hundreds of exercises/sets) that a sequential client-side version would be slow and have no rollback on partial failure. Every `program_day` materializes a `workouts` row, including empty rest days.

`start_program` has since been replaced several times (signature unchanged) to stamp copy attribution (`is_copy`, `is_imported`, `copied_from_*`) and the day's notes onto each workout it materializes; `copy_program` builds on it. Any further change to `start_program` must start from its newest definition, currently `20261110001658_add_ai_import_accept.sql`, not the original file.

**Never add a second foreign key between two tables the app already embeds through PostgREST.** `workouts` and `programs` each have a `user_id` FK to `profiles`, and the app embeds `profiles(display_name)` on them; a second FK to `profiles` makes PostgREST reject every such embed as ambiguous (`PGRST201`). Because migrations deploy ahead of app code, that breaks the app version already in production the moment the migration lands. This is why `copied_from_user_id` references `auth.users` (not exposed through PostgREST) instead of `profiles`. Widget tests can't catch this (they never hit the database) — check any new FK against the app's embedded selects on a local stack.

**Position/sequence fields must be derived from `max(existing) + 1`, not a count.** `ProgramDetailNotifier.addWeek`/`addDay` (`lib/features/programs/providers/program_detail_provider.dart`) used to compute the next `week_number`/`position` from `weeks.length`/`totalDays`. Deleting a week or day from the middle of a program left the count behind the highest number still in use, so the next insert collided with a surviving row and threw on the `program_weeks_program_id_week_number_key` / `program_days` position unique constraint — fixed by deriving from `max(existing) + 1` instead. The same "position = count" shape still exists in `addDay`'s `day_number: week.days.length + 1` (harmless — `day_number` is intentionally not unique) and `addExercise`'s `position: day.exercises.length` (`program_exercises.position` has no unique constraint either, so it won't crash, but can still produce silently wrong ordering after a mid-list delete). Treat any new `position`/`order` assignment in this codebase with the same suspicion.

## CI/CD

- `.github/workflows/pr-checks.yml` — six parallel job definitions, no `needs:` between them: `checks` (`./scripts/check-generated.sh`, `flutter analyze`, `flutter test`), `build-web` (matrix over `release`/`debug`/`profile`), `build-android` (matrix over the same three modes, APKs), `build-ios` (`flutter build ios --release --no-codesign` on `macos-26`), `db-validate` (`supabase db reset` + `db lint` + `test db`), and `e2e` (see E2E tests below). Both build matrices use `fail-fast: false` so one broken mode doesn't hide the others; release APKs are signed with the debug keys, so no signing secrets are needed. The builds are deliberately separate from `checks` — the Gradle build dominated it and was delaying analyze/test feedback. Only `build-android` sets up Java; the other jobs don't need it.
- `.github/workflows/self-hosted-test.yml` — runs every 4 hours on a schedule (`0 */4 * * *`, UTC, against `main` only, since scheduled runs always use the default branch) and on demand via `workflow_dispatch`, on the self-hosted `arc-runner-set`: a `test` job (analyze + tests + coverage) and a `build-web` matrix (`release`/`debug`/`profile`) in parallel. Keep its Flutter version pin in sync with `pr-checks.yml`; it appears in both jobs.
- `.github/workflows/deploy.yml` — on push to `main`, builds and publishes the web app to GitHub Pages (with `--base-href` set to the repo subpath).
- `.github/workflows/deploy-ios.yml` — on push to `main` (its own `paths-ignore`, which keeps `ios/**`), archives a signed release build on `macos-26` and uploads it to TestFlight. Signing is cloud-managed through an App Store Connect API key (`APP_STORE_CONNECT_KEY_ID`/`_ISSUER_ID`/`_API_KEY_P8` secrets) and `-allowProvisioningUpdates`, so no certificate or profile is stored. `ios/ExportOptions.plist` has `destination=upload`, so the export step is also the upload. It uses `flutter build ios --config-only` + raw `xcodebuild` because `flutter build ipa` can't pass the API-key flags. Version comes from `version.yml`, the same as the web deploy. Setup checklist: `docs/build.md`. The Flutter pin in `pr-checks.yml`, `deploy.yml`, `deploy-ios.yml` and `self-hosted-test.yml` must move together.
- `.github/workflows/deploy-functions.yml` — on push to `main` touching `supabase/functions/ai/**`, deploys the `ai` edge function with the CLI (needs the `SUPABASE_ACCESS_TOKEN` secret), then checks that a request with no session gets a 401. Its CLI pin moves with `pr-checks.yml`.
- `.github/workflows/ai-import-cleanup.yml` — daily at 09:17 UTC, and on demand, POSTs to the `ai-import-cleanup` function with the `AI_IMPORT_CLEANUP_SECRET` repository secret. The same value must be set as the function secret on the hosted project. The run fails on anything but 200, including partial failures, so problems show up in Actions.
- Migrations are deployed **separately**, by the Supabase GitHub integration watching `supabase/`. The two are unordered relative to each other, so ship additive migrations ahead of the code that depends on them.

## Testing

Widget tests stub data by **subclassing the generated notifier and overriding `build()`**, then passing it to `ProviderScope(overrides: [...])` — e.g. `workoutsProvider.overrideWith(() => _EmptyWorkoutsNotifier())`. Simple derived providers use `overrideWithValue` (`unitPreferenceProvider.overrideWithValue('kg')`). There is no Supabase mock; tests never hit the network. Pure logic (parsers, resolvers, model JSON) is tested directly without widgets.

### E2E tests (`integration_test/`)

`flutter test` only runs `test/`; the E2E suite is separate and always goes through its runner:

```bash
./scripts/e2e.sh          # macOS desktop (default)
./scripts/e2e.sh linux    # Linux desktop, how CI runs it
```

The script starts the local stack, runs `supabase db reset` (local only — never `--linked`), then runs each test file. Unlike widget tests, these boot the **real app against real Supabase**: no provider is stubbed. That's forced by `RouterNotifier.redirect` in `lib/app.dart`, which reads `Supabase.instance.client.auth.currentSession` directly rather than through a provider, so it can't be overridden — anything past `/` needs a genuine session. Tests sign in as the seeded `a@a.com` / `123456`. Locally the script passes the same `.env.local.json` used for a normal run; in CI, where that gitignored file doesn't exist, it instead reads `API_URL`/`PUBLISHABLE_KEY` straight off the running stack via `supabase status -o env`.

Rules for adding to the suite:

- **Never call `flutter test integration_test` on the whole directory.** Each file launches a real desktop app window, and a second launch inside one invocation fails with `Unable to start the app on the device`. `scripts/e2e.sh` loops one invocation per file for this reason.
- **Go through a page object** in `integration_test/support/pages/`, never raw finders in a test body.
- **Target keys, not text**, for anything you interact with — add a `Key('screen_thing')` to the widget in `lib/` as needed. Nav tabs and bottom-sheet entries are the exception; their labels are unambiguous.
- **Use `waitFor` / `waitForAbsent` from `support/harness.dart`** after anything that hits the network. A bare `pumpAndSettle` blocks on the spinner that's still on screen and reports a far less useful failure.
- **Assert presence, not counts.** The suite must stay green re-run against a stack that wasn't freshly reset.
- The harness initializes Supabase with `EmptyLocalStorage` so sessions never persist to disk. Don't remove that: with the default storage, a session from a previous run is restored *asynchronously* during `initialize` and races the sign-out, which makes only the first test of a run fail.
- Both desktop targets are wider than the 600px `kMobileBreakpoint`, so these exercise `AppShell`'s `NavigationRail` branch. The mobile `BottomAppBar` branch stays widget-test territory.

**Widget tests render in `flutter_test`'s default ~800x600 surface.** A screen taller than that (nested `ExpansionTile`s, long lists) can push a target below the visible area — `tester.tap(finder)` on an off-screen widget doesn't throw, it just misses (a "hit test warning" that's easy to miss in the output), and the real failure surfaces later as something confusing and unrelated-looking, e.g. `Bad state: No element` from `enterText`/`showKeyboard` because a dialog never actually opened. Call `await tester.ensureVisible(finder); await tester.pumpAndSettle();` before tapping anything that might sit below the fold. After any UI change that adds height to a screen (more padding, more content), re-run the full suite rather than just the file touched — layout-adjacent tests can break invisibly.
