# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

NoMoreX — a Flutter (mobile + web) strength-training log backed by Supabase. Users record personal bests (PRs), build workouts out of exercises, and program sets either as an absolute load or as a percentage of their 1-rep max.

## Commands

Every `flutter` command that runs or builds app code needs the Supabase config injected at compile time (see "Configuration" below), otherwise the app builds fine but silently cannot reach Supabase.

```bash
flutter run --dart-define-from-file=.env.local.json  # local `supabase start` stack (APP_ENV=local, no telemetry)
flutter run --dart-define-from-file=.env.beta.json   # the hosted beta Supabase project
# On Android, iOS and macOS also pass the matching flavor: --flavor local / beta / production (no default; a mismatch with APP_ENV throws at startup)

flutter analyze                    # lints (flutter_lints + riverpod_lint, an analyzer plugin)
flutter test                       # full suite
flutter test test/workouts/set_editor_test.dart                  # one file
flutter test --plain-name 'add-exercise picker shows options'    # one test

./scripts/gen.sh                   # regenerate *.g.dart (cleans the build cache first)
dart run build_runner watch
```

**Run `build_runner` before every commit that touches a file with a `part '*.g.dart';` directive, and commit the regenerated `*.g.dart` alongside it.** The generated files are committed, and they copy more than signatures: each provider's doc comment, and a hash of its body. So a comment edit or a change inside a provider's function body makes its `.g.dart` stale even though `flutter analyze` and the app are both fine. Only a signature, name or annotation change breaks analyze. CI's `checks` job runs `./scripts/check-generated.sh`, which regenerates everything and fails the PR on any difference. Run it yourself after committing and before opening a PR; it compares against git, so uncommitted generated files show up as differences. If it reports files you didn't touch, they went stale in an earlier commit; regenerate and commit them in their own `chore:` commit rather than reverting them. Use the script rather than a bare `build_runner build` to check: a plain build trusts its cache in `.dart_tool/build` and can skip a stale file, writing nothing, so the script runs `build_runner clean` first. For the same reason, regenerate with `./scripts/gen.sh` rather than a bare `build_runner build`, which can also stall silently on a stale cache. (`--delete-conflicting-outputs` is now ignored by build_runner.)

**The Dart MCP server is configured for Claude Code** (`.mcp.json` → `scripts/dart-mcp.sh` → `dart mcp-server`, details in `docs/build.md`). Prefer its `lsp` tool over text search when finding references or definitions before renaming or changing a signature: Riverpod's generated names (`fooProvider` from `Foo`) make grep miss uses. Keep `dart-mcp.sh` silent on stdout, which is the protocol stream.

**Cloud sessions have no display or keyring, so run E2E under xvfb and `with-keyring.sh`:** `xvfb-run -a ./scripts/with-keyring.sh ./scripts/e2e.sh linux` (`./scripts/verify.sh` already does this there, and runs the macOS target on a Mac). Without xvfb the desktop app can't open a window, and without an unlocked keyring its first key-storage read crashes it.

**Driving the web app in cloud sessions (headless Playwright):** `flutter build web --debug --dart-define-from-file=.env.local.json`, then `node scripts/web-shot.mjs <route> <out.png> [--flow scripts/web-flows/<flow>.mjs]`. It signs in as `a@a.com`, turns on Flutter's accessibility tree, runs the optional flow, and screenshots the route. **Drive flows with role locators**, e.g. `page.getByRole('button', { name: 'Add sets (%)' })`, `getByRole('switch', { name: 'Rep range' })`, `getByRole('button', { name: 'Increase Reps' })` (each `NumberStepperField` names its buttons `Decrease <label>` / `Increase <label>`). These find widgets by what they say rather than where they are, and every tap lands. Coordinate clicks (`page.mouse.click(x, y)`) still work as a fallback, but they drift with layout and occasionally drop taps on small targets like switches. A widget with no visible text or semantics label (a bare `IconButton`) has no name to find it by — give it a `tooltip` or `Semantics` label, which also fixes it for screen readers. **Don't put a separate button inside a `ListTile`/`CheckboxListTile`** (`trailing`/`secondary`): the tile merges its children into one semantics node, so the button is announced as part of the tile and can't be activated on its own. Widget tests won't notice, because they tap by position. Put it beside the tile in a `Row`, as `WorkoutDetailScreen`'s log chip does (`LogSetChip`, its own `Semantics(container: true)` node). `scripts/web-flows/add-pr.mjs` is an older, coordinate-driven example that writes a PR to the local stack.

**Visually testing the web app via claude-in-chrome:** `flutter run -d chrome --dart-define-from-file=.env.local.json --web-port=<PORT>` launches its own dedicated Chrome instance for Flutter's debug service — that instance is not the one claude-in-chrome controls. Run it in the background, then navigate a claude-in-chrome-controlled tab to `http://localhost:<PORT>` directly; it's a normal web server, so any browser tab can load the running app there. Requires the local Supabase stack up (`supabase start`) first.

Expect **rendering** to be verifiable this way and **tapping** not to be. Navigating straight to a route via the URL hash (`http://localhost:<PORT>/#/community/<id>`) reliably lands on any screen, and a signed-in session persists across reloads. But synthetic clicks land inconsistently on Flutter's canvas: large `FilledButton`s and the DOM-backed login inputs work, while list tiles and inline `WidgetSpan`-wrapped `InkWell`s can silently do nothing — no console error, no navigation — and dispatching `PointerEvent`s at `<flutter-view>` via the JS tool doesn't help either. Use the browser to confirm what a screen *looks* like, cover tap-driven behavior with widget tests, and after 2-3 failed clicks say plainly what's unverified rather than retrying.

Database (requires Docker + Supabase CLI):

```bash
supabase start
supabase migration new <name>   # never hand-name migration files
supabase db reset               # replay all migrations from scratch — do this before pushing
supabase db lint
supabase test db --local        # pgTAP tests in supabase/tests/database/
supabase status                 # prints local URL + publishable key for .env.local.json
```

AI edge function (Genkit; details in "AI / Genkit" below and `docs/build.md`):

```bash
supabase functions serve ai                         # local; needs supabase/functions/.env with ANTHROPIC_API_KEY
(cd supabase/functions/ai && deno task check)       # fmt + lint + type-check + unit tests, as CI runs it
```

**Never run `supabase db reset` (or any `--linked` variant of it) against a hosted or linked project (beta today, production later).** It drops and recreates the database, which deletes real user data. `db reset` defaults to `--local` and that's the only form that should ever run in this repo or in CI. If asked to reset the linked/remote project, always stop and ask for explicit confirmation first, and be clear that it is a destructive action that can delete user data.

## Cloud sessions (Claude Code on the web)

The `SessionStart` hook sets up the CI toolchain and a local Supabase stack (see `docs/build.md`). Before calling a change done, run `./scripts/verify.sh` and report its summary as is. If a stage shows `SKIP`/`WARNING` (e.g. Docker unavailable), say that stage is unproven rather than implying it passed.

## Improving the development setup

Cloud or local, when something about the setup slows the work down or leaves a check unproven, suggest the fix: a missing tool, a flaky or slow step, a manual workaround you had to repeat. Examples are a tool `verify.sh` had to fall back for, or a script future sessions will need. Say what you'd change and why, and offer to add it to the current branch. Development improvements are welcome in feature work, as their own `chore:`/`ci:`/`docs:` commit so the feature commit stays reviewable. Don't make the change without asking, and mention it in the PR description.

Where a fix goes:
- **Cloud provisioning** lives in the repo, not in the environment's settings: `scripts/cloud-setup.sh` for slow installs (cached with the environment), `.claude/hooks/session-start.sh` for per-session steps and for filling in anything older cached setups lack, and `scripts/lib/cloud.sh` for shared helpers. Read tool versions from the composite actions in `.github/actions/` with `read_pins` rather than adding another pin. Change the environment itself (network hosts, variables) only when the repo can't do it.
- **Local development:** `scripts/` and `docs/build.md`. Prefer a script over a written-out sequence of commands.
- **Checks:** `scripts/verify.sh`, and `pr-checks.yml` when CI should run it too.

## Environments: every external dependency is split by environment from day one

There are three environments: `local` (developer machines and cloud agent sessions), `beta` (everything deployed today: TestFlight, GitHub Pages) and `production` (reserved for the official App Store, Google Play and the official website; nothing sends `production` until that launch). **Any new external dependency or third-party service (an API, a SaaS, a key, a bucket, a webhook, a workflow secret) must be set up per environment from the start**: its own project/instance/credentials for `local`, `beta` and `production` (the word "test" is not used for an environment, flavor, bundle ID or GitHub Environment), selected by the environment and never shared across them, even if `production` is only provisioned at launch. Say which per-environment values it needs and where each is configured (define files, repo/environment secrets, function secrets) in the same PR that adds it, and update this section. **Android, iOS and macOS each have a flavor per environment** (`local`, `beta`, `production`, with application ids `com.nomorex.app.local`, `.beta` and `com.nomorex.app`), so the three install side by side: a platform setting that differs by environment goes in the Gradle `productFlavors` and the three `Environment-*.xcconfig` files, never in a shared file (the launcher icon is one: beta's is blue-slashed, see `docs/build.md`, "App icon and splash screen"). Details and the Firebase config per flavor are in `docs/build.md`, "Platform flavors"; `test/core/environment_identity_test.dart` keeps the platforms in step.

## Configuration

`lib/main.dart` reads `SUPABASE_URL` and `SUPABASE_PUBLISHABLE_KEY` via `String.fromEnvironment()`. These are **compile-time** constants, not runtime env vars — OS environment variables have no effect; the values must arrive via `--dart-define` / `--dart-define-from-file`. Unset values default to empty strings with no error. `.env.beta.json` (hosted beta) and `.env.local.json` (local stack) are gitignored and created per machine; each sets `APP_ENV` (`local`, `beta` or `production`; unset means `local`; read through `AppEnvironment` in `lib/core/environment/app_environment.dart`, which throws on an unknown value). Android emulators reach a local stack at `10.0.2.2`, not `127.0.0.1`. `SENTRY_DSN` works the same way, and only `.env.beta.json` has one. So do `SENTRY_RELEASE` and `SENTRY_DIST`, which only the deploy workflows pass. **Telemetry (Sentry events and analytics) is sent only by release builds of `beta` and `production`** (`collectsTelemetry()`); a debug or profile build never sends it, whatever `APP_ENV` says, unless built with `--dart-define=TELEMETRY_DEBUG=true`, and those events are tagged `local`, so they never mix into beta's data. The deploy workflows build with `APP_ENV=beta`, which is what Sentry reports as the environment. Full details in `docs/build.md`.

## Architecture

**Feature-first layout.** `lib/features/<feature>/{models,providers,screens,widgets,utils}`, with `lib/core/` (constants, theme, unit conversion, date formatting) and `lib/shared/widgets/` for cross-feature pieces. Features: `ai`, `analytics`, `auth`, `community`, `dashboard`, `exercises`, `personal_bests`, `profile`, `shell`, `workouts`, `programs`.

**No repository/service layer.** Riverpod notifiers talk to `Supabase.instance.client` directly, and mutations end with `ref.invalidateSelf(); await future;` so callers can `await` a completed refetch. Follow that shape rather than introducing a data-access abstraction.

**`invalidateSelf()` is rarely enough — several keepAlive providers cache the same rows.** `workoutsProvider`, `archivedWorkoutsProvider`, `inProgressWorkoutsProvider`, `finishedWorkoutsProvider` and `communityWorkoutsProvider` all run their own `select('*, workout_exercises(*, exercises(name))')`, so a workout's exercises are cached in as many places as there are lists showing it. A mutation must invalidate every provider whose *rendered output* changes, not just the one it was called on: `WorkoutDetailNotifier.addExercise`/`removeExercise` invalidate `workoutsProvider` because the Workouts list renders `w.exercises.length`, and `PersonalBestsNotifier.addPr` invalidates both `oneRepMaxProvider` and `oneRepMaxByNameProvider`. Skipping this doesn't fail loudly — the stale value just sits there until some unrelated mutation happens to refetch, which is why "it's wrong until I refresh the page" bugs in this codebase are almost always a missing cross-provider `ref.invalidate`.

**Reading an async provider inside a callback: `await ref.read(p.future)`, not `ref.read(p).asData?.value`.** These providers are `keepAlive` but still lazy, so if nothing in the current screen `watch`es one, `.asData` is `null` at the moment a tap handler runs — indistinguishable from a legitimately empty result. `SetPrLink` (`lib/shared/widgets/set_pr_link.dart`) awaits the future for exactly this reason: treating "not loaded yet" as "the user doesn't have this exercise" would silently create a duplicate.

**Rendering an async provider that can fail: `whenLoaded()`, not `when()`, and never the raw error.** Riverpod retries a failed load on its own, and while it does the state is a reload that still holds the error, which `when()` renders as loading: the screen spins through every backed-off retry before the failure appears. `whenLoaded()` (`lib/shared/widgets/load_failure.dart`) shows the error builder instead. Fill it with `LoadFailureView` for a screen or list ("Couldn't load this workout", Try again → `ref.invalidate(provider)`) or `LoadFailureRow` for one section of a page, passing `async.retrying` so it says "Trying again…". `$e` names the backend (`PostgrestException…`) and means nothing to a lifter, so it never reaches the screen.

**Auth-scoped providers.** Every provider that reads user data is `@Riverpod(keepAlive: true)` and starts with `ref.watch(authStateProvider)` before reading `currentUser?.id`, returning empty when null. `authStateProvider` wraps `onAuthStateChange`. Omitting that watch leaks the previous user's data across a sign-out — keep it in any new data provider.

**Models are hand-written.** Plain immutable classes with a `fromJson` factory; no freezed or json_serializable. Nested Supabase selects (`select('*, workout_exercises(*, exercises(name))')`) are unpacked inside the parent's `fromJson`, which also sorts children by `position`. Match that pattern when adding a model.

**Routing** lives entirely in `lib/app.dart`. `RouterNotifier` listens to `authStateProvider` and redirects: unauthenticated users off any non-public route to `/`, authenticated users off `/` and `/login` to `/shell/home`. The shell tabs are a `StatefulShellRoute.indexedStack`; detail/edit/create routes sit outside the shell. All paths are constants in `lib/core/constants/app_constants.dart` — add new ones there, not as string literals.

**Theme: Sleek Orange v3, light and dark.** `AppTheme.light()` / `AppTheme.dark()` (`lib/core/theme/app_theme.dart`) build both themes from one set of component rules and two `NomorexPalette`s; `app.dart` follows the device setting (`ThemeMode.system`). The design system itself (tokens, components, usage rules) is the "Sleek Orange Design System" artifact; token names in `NomorexPalette`/`NomorexTokens` match it one to one. **One accent, so `ColorScheme.secondary` is a trap:** `secondary`/`tertiary` and every `*Container` role are pinned to the orange (or its subtle wash) so stock M3 widgets don't fall back to Material's baseline purple/teal — reaching for `colorScheme.secondary` to get "the other color" silently gets you orange. `colorScheme.error` is the danger *text* color (validation and failure messages); destructive button fills come from `NomorexTokens.dangerButtonStyle`. Anything without a stock slot lives on the `NomorexTokens` extension — read it with `NomorexTokens.of(context)`, which falls back to the same stock tokens in widget tests that build a bare `MaterialApp`. Inter and JetBrains Mono are bundled under `assets/fonts/` and declared in `pubspec.yaml` (licenses registered in `main.dart`); don't reintroduce runtime font fetching such as `google_fonts`, which leaves text in the system font offline and contacts Google on every install. The blue is `NomorexTokens.info` (text only, never a button); the neutral equal-weight button is `secondaryButtonStyle`; weights render in the mono `weight`/`weightMd`/`weightLg` styles; mono caps section labels use `eyebrow`. Related rows go in one bordered `ListGroup` (`lib/shared/widgets/list_group.dart`) rather than a card each — row widgets built on `GroupableTile` drop their card chrome automatically inside one. Add new design tokens there rather than hardcoding a `Color` at the call site.

**Admin area: `lib/features/admin`, admins only.** Profile shows an "Admin" button when `isAdminProvider` is true, opening the hub at `/admin`. The hub lists `kAdminSections` (`models/admin_section.dart`), filtered by each section's `requiredRole`, so **a new admin feature is one `AdminSection` entry plus a child route under `/admin` in `app.dart`**, backed by a server function like those in Database below. The `/admin` route's `redirect` (`adminRouteRedirect`, which awaits `currentUserRolesProvider.future`) sends anyone else to Profile, including on a deep link, and covers the child routes. `RouterNotifier` listens to the roles so a revoked admin is moved off. Each screen is also wrapped in `AdminGate`. None of this is security: the server refuses every admin call from a non-admin. Admin calls fail with a `code: detail` message, so show `adminErrorMessage()` (`utils/admin_error.dart`) rather than the raw error. Roles are strings (`AppRoles`), not an enum, so a role added on the server doesn't break an older app. The users table (`adminUsersProvider`, a family over search and page) and the audit log (`adminAuditLogProvider`) are auto-disposed so each visit re-reads; a role change (`AdminRolesNotifier`) invalidates both plus `currentUserRolesProvider`, and the role switches come from the `roles` table (`availableRolesProvider`), so a new role needs no UI change.

**Responsive shell.** Below 600px (`isMobile()` in `lib/shared/widgets/responsive_layout.dart`) `AppShell` renders a bottom bar of the three tabs plus a fourth **New** item that opens the New sheet. There's no FAB, so nothing floats over a page and lists need no extra bottom clearance. From 600px up, `AppFrame` (`lib/features/shell/app_frame.dart`), the builder of an outer `ShellRoute` around **every signed-in route** in `app.dart`, puts `AppSidebar` beside the page, so navigation stays on detail and edit screens too; `AppShell` then just shows the tab. A new signed-in route goes inside that `ShellRoute`. The sidebar's selected section comes from the path (`navSectionFor()` in `nav_section.dart`), so a new top-level path prefix needs a case there. Page content centers in the space beside the sidebar because `contentInset()` subtracts `SidebarInset.widthOf(context)`; use `contentPadding()`/`shellListPadding()` rather than measuring `MediaQuery` width yourself. Detail screens title themselves with `BreadcrumbTitle`, which leads with the section beside the sidebar (inside Training, with the Training view: "Programs › ZT 6 Week Program", via `trainingViewFor()`) and is the plain title on a phone. The page side of `AppFrame` is its own `Semantics(container: true)`: without it each page's route barrier hides the whole sidebar from screen readers (`app_sidebar_test.dart` guards this). Collapsed/expanded is `sidebarCollapseProvider`, saved with `shared_preferences`. There are 3 shell tabs (Home, Training, Community), listed once in `NavSection.tabs`; both the phone bar (which adds New after them) and the sidebar loop over it, and its order must match the `StatefulShellRoute` branches in `app.dart`. What "New" offers is `kNewItemActions` in the same file.

**Training is one tab holding programs, workouts and PRs** (`lib/features/training/`, #141). `TrainingScreen` owns the app bar (Refresh, a History action that follows the view, none on PRs, and Profile on a phone) and a `TabBar` (styled like Community's; its controller only follows the route, and the body stays an `IndexedStack`, so no swipe changes the view behind the URL's back) over `ProgramsView`, `WorkoutsView` and `PrsView`, which are bodies with no `Scaffold` of their own. Each view has its own path, `/shell/training/programs|workouts|prs` (`AppConstants.routePrograms` etc., and the `TrainingView` enum in `nav_section.dart`), so a tab tap navigates with `context.go` and back and links land on the right view. The routes are built in `training_routes.dart`: one `:view` route whose `NoTransitionPage` keeps a constant key, so switching keeps the same `TrainingScreen` and its `IndexedStack` keeps each view's search and scroll; a view is built only once it's first shown. The bare `/shell/training` reopens the view used last (`TrainingViewNotifier`, saved in `shared_preferences`), and its redirect is async so it waits for the saved value rather than defaulting to Programs on a cold start. The old `/shell/programs`, `/shell/workouts` and `/shell/prs` redirect (`legacyTrainingRedirects`). Programs and Workouts switch to their archived lists with `ArchivedToggle` beside search, not a tab bar.

**Programs are authoring-time templates; Workouts stay the only runtime/logged entity — but a program run is tracked.** A `Program` is a reusable template (`programs -> program_weeks -> program_days -> program_sessions -> program_exercises -> program_sets`, mirroring the `workouts -> workout_exercises -> workout_sets` shape one level deeper, minus logging fields). "Starting" a program calls the `start_program` RPC, which inserts a `program_instances` row and bulk-materializes the template into ordinary `workouts`/`workout_exercises`/`workout_sets` rows stamped with `program_instance_id`/`program_day_id`/`program_session_id` (see Database below) — logging itself is still just a normal workout through the existing screens. On top of that, the instance is surfaced back to the user: the dashboard's "Current Programs" section and `ProgramInstanceDetailScreen` (`lib/features/programs/screens/`) read active `program_instances` to show upcoming/in-progress status and highlight today's day (`isProgramDayToday` in `utils/program_progress.dart`), and `WorkoutsNotifier`'s query excludes any workout with a non-null `program_instance_id` so materialized workouts don't flood the general Workouts list — they're reachable only through the instance screen, whose day cards push straight to the real `WorkoutDetailScreen`. **Editing a program is two editors, chosen by width.** `/programs/:id/edit` renders `ProgramEditEntry`, which shows the one-page `ProgramEditScreen` from 600px up and, on a phone, the drill-down in `lib/features/programs/screens/edit/`: `ProgramEditOverviewScreen` → `/programs/:id/edit/weeks/:weekId` (`ProgramWeekEditScreen`) → `/programs/:id/edit/days/:dayId` (`ProgramDayEditScreen`), with each exercise edited in a bottom sheet (`showExerciseEditSheet`). **A week is a calendar week: at most 7 days** (`kMaxDaysPerWeek`, `ProgramWeek.isFull`; the database refuses an 8th with `week_full`, see Database). Add week creates Day 1–7 as rest days (`add_program_week`), and adding an exercise to a rest day makes it a training day (`ProgramDetailNotifier.addExercise`; both editors offer Add exercise on a rest day). Add day appears only on a week with fewer than 7 days, for getting back to 7 after a delete, and Duplicate day / Copy to other weeks skip full weeks. **A day holds 1–3 sessions, each its own workout** (`ProgramSession`, `kMaxSessionsPerDay`, #175; the database refuses a 4th with `day_full`). Every day the app creates has one, and a one-session day shows no session chrome, so programs look as they did; `ProgramDay.exercises` is a getter flattening the sessions, so read-only code needs no change. Both editors offer Add session under a training day with room, and a split day lists each session under a header with its own ⋯ menu (`showSessionActions`: rename, notes, duplicate, move up/down, remove; never on the last session) and its own Add exercise (`addExercise(..., sessionId:)`). A run keys its workouts by session (`workoutKey()`: `program_session_id`, else `program_day_id`), shows a row per session titled like its workout ("Day 1 · AM", `programSessionTitle`), and checks a day only once every session is finished; stats count one workout per session (`StatsDay.workoutKeys`). Weeks are reordered by dragging their cards on the overview, and days by dragging theirs on the week screen (`reorderDays`, within the week); neither ⋯ menu has move entries. The week strip and day tabs `context.replace` the route so back goes up a level, and both screens' back arrow goes up even when opened from a link. Both editors write through the same `ProgramDetailNotifier` methods, so a fix to how something saves belongs there, not in a screen. Duplicate week/day and Copy to other weeks call the editor RPCs (Database, below) via `duplicateWeek`/`duplicateDay`/`copyDay`; the ⋯ menus live in `program_edit_actions.dart`. The editor's one-line summaries ("4 × 3 · 20 kg", "100% of Snatch") come from `utils/program_edit_summary.dart`: they show what was programmed, never a resolved load. Widget tests run at 800×600, which is the desktop editor; the phone editor's tests set `tester.view.physicalSize` (`test/programs/edit/`). The phone editor's exercise sheet edits sets as groups instead: `SetGroupEditor` (`lib/features/programs/widgets/set_group_editor.dart`) shows each run of identical consecutive sets (`groupConsecutiveSets`, which compares every prescription column and the per-set note) as one row, reopens the sets sheet pre-filled (`showPercentageSetsSheet`/`showAbsoluteSetsSheet` with a `SetsSheetInitial`) and saves the whole group through `ProgramDetailNotifier.replaceSetGroup`. "Edit the last set only" is how one set comes to differ. A new prescription field has to be carried through `SetsSheetInitial` and the group's prescription map, or editing a group drops it. `SetEditor` (`lib/features/workouts/widgets/set_editor.dart`) is shared between editing a workout and authoring a program via the `EditableSetRow` DTO (`lib/shared/models/editable_set_row.dart`); `WorkoutSet.toEditableRow()` / `ProgramSet.toEditableRow()` map into it.

**Usage analytics: Google Analytics for Firebase, behind `AppAnalytics` (`lib/features/analytics/`).** Sentry keeps errors and crashes. Log through `ref.read(analyticsProvider).logEvent(AnalyticsEvents.x, {...})` after the action succeeds, never through `FirebaseAnalytics` directly. `analyticsProvider` is a no-op unless `initFirebase()` ran, so widget tests and Linux/Windows need no override and never reach Firebase, and calls never throw. Add a new event name to `AnalyticsEvents`. Params are `String`/`num` only and **never personal data or anything the user typed**: no names, emails, notes, exercise names or record IDs. Screen views are logged by `trackScreenViews()` from the router, named by route pattern (`/workouts/:id`), so a new route needs nothing. Each environment reports to its own Firebase project, chosen by `firebaseOptionsFor()` (`lib/features/analytics/firebase_environment.dart`): beta is the existing one, `local` starts no Firebase, and production has none yet (add its options there when it exists). Each Android flavor builds against its own `google-services.json` and each iOS/macOS flavor copies its own `config/<env>/GoogleService-Info.plist` in a build phase; only `beta` has either. Only release builds of `beta` and `production` collect (`TELEMETRY_DEBUG=true` for DebugView, see Configuration), and on web a build that doesn't collect skips Firebase entirely. **`main` must never block on Firebase:** on web its SDK comes from `www.gstatic.com` and never completes if that's blocked, so `initFirebase()` runs through `runFirebaseInit()` with a timeout. Keep any new Firebase startup work inside it. The user can also opt out in Profile (`AnalyticsConsentNotifier`). The app never calls `setUserId`, and advertising IDs are off: the iOS jobs build with `FIREBASE_ANALYTICS_WITHOUT_ADID=true` and `scripts/check-ios-no-adid.sh` fails a build that bundles the ad-ID SDKs. That variable is silently ignored once SwiftPM has cached manifests (`docs/build.md`, "Firebase"). The privacy policy, `PrivacyInfo.xcprivacy` and the store answers all say "not linked to the user", so linking analytics to the account is a privacy-policy change. Setup and regeneration: `docs/build.md`, "Firebase".

**AI / Genkit: one edge function, `supabase/functions/ai`, Genkit JS + `@genkit-ai/anthropic`, served through `@genkit-ai/fetch`.** The Anthropic key is a function secret and never ships in the app. Each Supabase project (beta now, production at launch) has its own key and its own spend limit; none is shared across environments. TypeScript rather than Genkit Dart because Supabase Edge Functions only run Deno. Each flow is `flows/<name>.ts` exporting `define<Name>(ai, model)`, registered in `flows/mod.ts`, and served at `POST /functions/v1/ai/<flowName>` with body `{"data": …}`. The client calls it with `callGenkitFlow()` (`lib/features/ai/utils/genkit_call.dart`), which goes through `functions.invoke` (session JWT attached automatically) and turns every failure into a `GenkitFlowException`. Rules that fail quietly if broken:
- **Data access goes only through the caller's RLS-scoped client.** `supabaseAuth` (`auth.ts`) verifies the JWT and puts `{auth: {uid}, supabase}` on the flow context. Every flow starts with `requireUserContext(context)`, and every flow in `mod.ts` is wrapped with `withActionOptions(…, {contextProvider: auth})`. **Never create a service-role/secret-key client there.** It would bypass RLS, and a prompt-injection bug would become a cross-user data leak.
- **Wrap every `ai.generate` in `callModel()` (`genkit.ts`).** Without it, a bad Anthropic key surfaces as `UNAUTHENTICATED`/401 with the provider's raw error. The app can't tell that apart from an expired session, and the message leaks upstream details. `callModel` logs the real error server-side and returns `UNAVAILABLE`, so 401 only ever means the user's session.
- **Don't rely on Zod `.default()` in flow input.** The HTTP handler doesn't apply schema defaults: `{"data":{}}` arrives with the field `undefined`.
- Import `retry` from `genkit/model/middleware`. `genkit/middleware` has types but isn't in the package's `exports`, so the worker fails to boot. Cap `maxDelayMs` so retries can't outlast the function's wall-clock limit.
- Pick models by tier (`MODELS` / `modelFor()` in `genkit.ts`), not raw IDs. The plugin resolves IDs it doesn't know by name, so a newer model needs no plugin bump.
- Context providers run only on the HTTP path. A flow started from the Genkit Dev UI's Run button has no user and fails `UNAUTHENTICATED` by design. Get traces by driving `dev.ts` over HTTP under `genkit start`.
- `.github/workflows/deploy-functions.yml` deploys the function with `verify_jwt` on. **Don't add `[functions.ai]` to `supabase/config.toml`:** the GitHub integration deploys anything declared there, bundles it server-side (5 MB limit), and fails with a 413. The CLI's Docker bundling allows 20 MB and the function is about 18.7 MB, so check the size before adding npm dependencies. Deno is pinned to 2.1.4 in `.github/actions/setup-deno` (which `verify.sh` and the cloud scripts read) to match the edge runtime.
- **`startAiImport` runs in the background and reads the model's reply as plain text on purpose.** It returns a job ID and finishes in `EdgeRuntime.waitUntil`; the job row is the only outcome the app sees. The model doesn't reliably follow a schema (`constrained: true` still returned out-of-enum values and code fences), so `ai_import/normalize.ts` parses the text and moves any bad value into a note or `unstructured` rather than failing the import. A program week holds at most 7 days, so `normalize.ts` splits numbered days into weeks of seven ("Day N" titles restart per week) and makes several entries on one weekday that day's sessions (`mergeSessions`), whatever the model returned. A day with 2–3 sessions comes back as `sessions` (import schema 2); a one-session day keeps `exercises` in the model's output to save tokens, and `normalize.ts` always writes `sessions`. Beyond 3, the rest are combined into the 3rd with an `unstructured` note. Results stored before #175 (schema 1, `exercises` on the day) still review and accept: the app and `ai_import_day_sessions()` read either. Every import has a `description`: the file's own introduction copied as written, or, when it has none, one or two sentences the model writes from what it read, marked `descriptionGenerated` so the review says so (it's an editable field there). `ai_import_create_program` saves it as the program's description, ahead of the notes that couldn't be placed anywhere (which used to be the whole description); `ai_import_create_workout` makes it the first paragraph of the workout's notes, since workouts have no description (`20261123052813_import_description.sql`). Change the output format in `ai_import/prompt.ts` and `normalize.ts` together, and in their Dart port (`packages/import_pipeline`, below) while both exist, and re-measure a 10-page file afterwards: output sits near the 20,000-token cap (17,649 on the dense synthetic test), and extra per-exercise fields can push it over. File type and size are checked from the bytes in `ai_import/file_check.ts` before any model call.
- **`supabase/functions/ai-import-cleanup` is the one function allowed a service-role key**, and it holds no AI code, so the `ai` function, which reads untrusted files, never gets one. It runs `ai_import_sweep()` (service_role only) and then deletes the returned upload folders through the Storage API. Deleting `storage.objects` rows in SQL leaves the stored files behind. It's declared in `config.toml` with `verify_jwt = false`, because its only caller sends the `AI_IMPORT_CLEANUP_SECRET` function secret rather than a session. It checks that secret itself and answers 503 while the secret is unset. A folder it fails to empty comes back from the next sweep, and that's the retry. The app deletes an import's files itself on accept or discard (`AiImportJobsNotifier.removeImportFiles`), so the sweep only catches what that missed, plus abandoned and orphaned uploads after 7 days.
- Tests: `deno test` with a fake model (`ai.defineModel`) and a fake Supabase client, no network. Flutter tests override the notifier's `callFlow()`. The debug-only Profile → "Test AI connection" button (`AiSmokeTestNotifier`, `smokeTest` flow) is the end-to-end check. `functions.invoke` doesn't consume SSE, so a streaming flow would need `package:genkit/client.dart`'s `defineRemoteAction` instead. **Any new user-facing AI feature needs a per-user cap like imports' (`ai_import_check()` counted on the server) before it ships;** the Anthropic account's spend limit is only a backstop.

**Bring your own AI: `lib/features/ai/core/` (epic #182).** The app calls AI itself through Genkit Dart: the lifter's own key for a cloud provider (`CloudAiProvider`: Gemini, Claude, ChatGPT) and the on-device model: Apple Intelligence since Stage 7, Gemini Nano and Chrome's from Stage 8. It replaces the hosted function above, which stays until Stage 12. Rules that fail quietly if broken:
- **Ask the router, never pick a model.** `modelForTaskProvider(AiTask.x)` returns an `AiRoute`, or null when nothing can run the task, and the feature hides itself then. `AiTask` says which side may run each task: imports run only on the cloud key, and the small editor helpers only on device, so they never spend the lifter's money unasked. Model IDs are in `kCloudModels` (tiers, like `MODELS` in `genkit.ts`).
- **Call models only through `generateWithRoute()`** (`ai_generate.dart`). Genkit doesn't throw when a model fails: it returns `finishReason: failed`. The wrapper turns that, and anything thrown, into an `AiProviderException` whose `message` is safe to show, retries outages (never rate limits or billing), and times out. Never show a provider's raw error.
- **Keys live only in `AiKeyStore`** (secure storage, one per provider; macOS needs `usesDataProtectionKeychain: false`). `AiSettings` records which keys exist, never their values. `genkitProvider` reads the key when it builds the plugin and rebuilds on every change (`keyRevision`). A device without working key storage (Linux without an unlocked keyring) gives `keyStorageAvailable: false`, not a crash. Keys never go to our server, analytics or Sentry: `beforeSend`/`beforeBreadcrumb` run `sentry_scrub.dart`, which strips key headers, `key=` parameters and anything shaped like a key.
- **A Gemini model must be one the plugin calls through `generateContent`.** `genkit_google_genai` sends every other name (the `-latest` aliases, `gemini-3.5-flash-lite`) to Google's Interactions API, which has no CORS headers, so on web the call fails before it reaches the model while native runs work fine. `model_router_test.dart` checks every Gemini entry in `kCloudModels` against the plugin's routing.
- **Apple Intelligence is the plugin package `packages/genkit_apple_intelligence`** (#189): Pigeon (`pigeon/messages.dart`) over Swift and Foundation Models, one shared `darwin/` source tree built by Swift Package Manager. `defineAppleIntelligenceModel()` registers `apple/foundation` on the Genkit instance (`genkitProvider` does it when `appleModelStatusProvider` says it's available), and `onDeviceStatusFromApple()` feeds `onDeviceAvailabilityProvider`. Rules that fail quietly if broken:
  - **The app's deployment targets stay at iOS 17 and macOS 12.** Every Foundation Models call sits behind `#available(iOS 26 / 26.4 / 27)`, which is why the framework is weak-linked (`otool -l` shows `LC_LOAD_WEAK_DYLIB`). Calls only an iOS 27 SDK has (image `Attachment`, `response.usage`, `capabilities`) also sit inside `#if compiler(>=6.4)`, and 26.4's (`contextSize`, `tokenCount`) inside `>=6.3`, so CI still compiles if its Xcode is older.
  - **Always cap the reply** (`maximumResponseTokens`; `kAppleDefaultMaxResponseTokens` when the request sets none): an uncapped run looped until it filled the context.
  - **JSON Schema becomes a `DynamicGenerationSchema`** (`SchemaConverter.swift`, from the #183 spike). `$defs` keep their exact names, or Apple fails with `undefinedReferences`. A schema it can't express (a free-form map) comes back as `schemaUnsupported`, and the Dart side retries with the schema in the prompt; keep task schemas translatable, because that fallback's output is loose.
  - **Errors cross the bridge as `PigeonError`s** (a `FlutterError` isn't a Swift `Error` on iOS), with codes the Dart side maps to the wording `aiExceptionFrom` already knows (`context window`, `Rate limit`, `unavailable`); a refusal is `FinishReason.blocked`.
  - **Pigeon output is committed**: after editing `pigeon/messages.dart`, run `./scripts/gen.sh`, which regenerates it too; `check-generated.sh` fails on stale `*.g.dart` or `*.g.swift`. The package's own tests (`flutter test` there, against a fake `AppleIntelligenceApi`) run in CI's `checks` job and `verify.sh`.
  - The availability is re-read on app resume (`AiImportJobAlerts`), since Apple Intelligence can be turned on in Settings meanwhile. Debug builds show "Try it (debug)" under the on-device row in AI assistant, which sends a real structured prompt.
- **Provider plugins load through `plugins/cloud_plugins.dart`'s `deferred as` imports,** so on web each SDK downloads only when used (+22 KB gzipped up front rather than +130 KB). Don't import a `genkit_<provider>` package anywhere else.
- **Settings live at Profile → AI assistant** (`AiAssistantScreen`, `/profile/ai-assistant`, #186): the on-device status, the provider choice, and each provider's key. "Save and test key" checks the key first through `aiKeyCheckerProvider` (a tiny request on the provider's fast model, because Anthropic's plugin hides a refused key when listing models) and saves it unless the provider refused it. A saved key is only ever shown masked (`maskKey`). The E2E test never saves or tests a key: Linux runners may have no keyring, and a test would call a real provider.
- **Imports run in the app when the lifter has a key** (#188). `aiImportPathProvider` picks the path: `local` (a key is set; it wins over the hosted alpha), `hosted` (no key, alpha switched on), `needsKey` (the import screen offers the settings) or `unavailable` (no key can be stored here and the alpha is off; only then are the entry points hidden, through `aiImportAvailableProvider`). `AiImportIntakeNotifier.submit()` follows it: `runLocally()` reads with `runImport()` (provider file limits from `aiImportIntakeLimitsProvider`), saves through `ai_import_save_result` and ends `started` with the job, which the screen opens in review. **The files never reach our server on this path, so the device is their only copy:** `ImportFileCache` (`utils/import_file_cache.dart`; the app support folder, memory on web) keeps them from the first try until the import is accepted or discarded (`AiImportJobsNotifier.removeImportFiles` clears both stores). That's what makes "Try again" after a failure or an app kill (`restoreUnfinished()`) and a re-run as the other type (`rerunFromCache()`, offered only while the device has the files; `AiImportReview.ranOnDevice`) work. Failures show `importFailureFor()`'s wording, never the provider's error. The per-provider notice is device-local (`aiImportNoticeProvider`), separate from the hosted `ai_import_consents`. Tests need `aiDeviceOverrides()` (`test/ai/core/ai_fakes.dart`) and mocked `SharedPreferences`, or the settings never load.
- **The import pipeline is the pure-Dart package `packages/import_pipeline`** (#187): the prompt (`kImportSystemPrompt`), the file checks and per-provider limits (`importFileLimitsFor`), `runImport()` and `normalizeImportResult()`, ported case for case from the edge function, whose output is the same stored JSON (`ai_import_results.payload`). No Flutter imports, so the benchmark runs it from the command line: `ANTHROPIC_API_KEY=… dart run tool/import_bench.dart --provider anthropic benchmark/dense_page.pdf` (`benchmark/README.md`; your own key, never the project's). The app's file checks re-export its byte sniffing. Its tests run with `dart test` in the package, in CI's `checks` job and in `verify.sh`, not under the root `flutter test`.
- Tests: `test/ai/core/ai_fakes.dart` has `FakeAiKeyStore` and `fakeGenkit()` (a Genkit with one `ai.defineModel` model); override `genkitProvider` and `aiKeyStoreProvider` with them.

## Domain rules

- **Weights are stored in kg everywhere** (`weight_kg`, `absolute_weight_kg`, `actual_weight_kg`). Convert only at the display/input boundary using `lib/core/utils/weight_converter.dart` and the user's `unitPreferenceProvider` (from `profiles.unit_preference`, defaults to `'kg'`).
- **Sets have three weight modes.** `weight_mode = 'absolute'` uses `absolute_weight_kg`; `'percentage'` uses `percentage` against the lifter's 1RM; `'open'` prescribes no load at all (both columns null), so the lifter picks the weight on the day, as for "Vert Pull 3×7–9, %1RM NA" or bodyweight work. `resolveSetWeightKg()` in `features/workouts/utils/set_resolver.dart` is the single place that resolves this, and returns `null` both when a percentage set has no 1RM to resolve against and for every open set — screens must handle that null rather than defaulting to zero, and must check `isOpenLoad()` first: an open set shows `kOpenLoadLabel` ("choose load"), never "0 kg" and never the `SetPrLink` shortcut, because there's nothing to resolve. Open sets are added from the weight dialog's "No set load" switch (`AbsoluteSetBatch.weightKg == null`). They're the one kind whose "Log set" sheet asks for the weight used on a live session (`WorkoutDetailNotifier.logSet`'s `weightKg`), which writes logging-only `actual_weight_kg`, never copied, like `actual_rpe`. A percentage set can also prescribe a **%1RM range** (`percentage_max`, e.g. 67–72.5%): screens that show a resolved weight use `resolveSetWeightRangeKg()` (same null rule, plus a `high` end resolved from the same 1RM) and render it with `formatResolvedWeightRange()`, so the ` (est.)` marker covers the whole range. Show a percentage with `formatPercentTarget()` (`core/utils/percent_range.dart`), never `toStringAsFixed(0)`, which turns 72.5% into "73%".
- **A percentage set's 1RM basis defaults to its own exercise, but can be a different one.** `workout_sets.basis_exercise_id` / `program_sets.basis_exercise_id` (nullable FK to `exercises`) let a set be programmed as e.g. "Front Squat @ 75% of Clean & Jerk". `resolveBasisExerciseId(set, exercise)` in `features/workouts/utils/set_resolver.dart` returns `set.basisExerciseId ?? exercise.exerciseId` — always look up `oneRepMaxProvider` by that, not by the set's own exercise id. The basis picker in `SetEditor`'s "Add sets (%)" dialog is unrestricted (any exercise in the catalog, not just ones already in the workout/program).
- **1RM is derived, not stored — and may be estimated.** `oneRepMaxProvider` maps `exerciseId -> OneRepMax` (`lib/shared/models/one_rep_max.dart`), taken from the user's *latest* `personal_bests` entry for the lift (by `date`, then `created_at`) whatever its rep count — the same entry the PRs card in Training shows as current, so a newer, lighter PR replaces an older, heavier one. A single is used as-is; a multi-rep entry is estimated. `OneRepMax.isEstimated` records which, and **every surface that renders a weight resolved from a 1RM must carry that flag through** — `formatResolvedWeight()` (`core/utils/weight_converter.dart`) appends the ` (est.)` marker, so use it rather than `formatWeightForPreference` for a resolved percentage weight. Estimation uses the user's `profiles.one_rep_max_formula` (Brzycki/Epley/Lander, default Brzycki) via `estimateOneRepMaxKg()` in `core/utils/one_rep_max_formula.dart`, and is withheld entirely outside 2..`kMaxEstimableReps` (10) reps — such an entry is skipped so the next most recent usable one wins, and a lift with only high-rep PRs is simply absent from the map, the same "no 1RM" state as having none. Both 1RM providers `ref.watch(oneRepMaxFormulaProvider)`, so changing the setting recomputes them; don't add a manual invalidation. Personal bests remain the source of truth for programming percentages. The **all-time best** that PR history shows is a different thing: the entry with the highest estimated 1RM under the same formula (`allTimeBest()` in `features/personal_bests/utils/all_time_best.dart`, earliest wins a tie, unestimable entries skipped). It's display-only — percentages still resolve from the latest entry, not the all-time best.
- **An `exercises.id` only means something inside one user's catalog — across users, match on name.** Two users who both have a custom "dude pulls" have two unrelated rows with different ids (there's no unique constraint on `name`, so duplicates by name are expected, not a data error). This matters everywhere a viewer looks at someone else's data: a public workout's `workout_sets.basis_exercise_id` points at the *owner's* exercise, while the viewer's PR for the same lift hangs off *their* id, so an id-keyed lookup silently misses forever. Resolve a viewer-facing 1RM through `lookupOneRepMax()` (`features/workouts/utils/set_resolver.dart`), which tries `oneRepMaxProvider` by id and then falls back to `oneRepMaxByNameProvider` by normalized name (official aliases included); when a viewer needs their *own* row for a foreign exercise, go through `ExercisesNotifier.ensureExerciseByName()`, which find-or-creates by name. The two halves must agree on name matching or a user can record a PR that never resolves anything. **"The same name" has exactly one definition, written three times:** `normalize_exercise_name()` in SQL, `normalizeExerciseName()` in Dart (`packages/import_pipeline/lib/src/exercise_name.dart`, which the app re-exports from `core/utils/exercise_name.dart`) and in the AI function (`ai_import/normalize.ts`): whitespace collapsed, trimmed, lowercased. Each one's tests run the same cases (`exercise_catalog.test.sql`, `exercise_name_test.dart`, `normalize_test.ts`), so change all three together. Picking a row for a name also has one order everywhere: an active official exercise by name **or alias**, then a retired official one, then the caller's oldest custom row (`find_exercise_for_user()` on the server, used by `map_exercise_for_viewer` and `ai_import_resolve_exercise`; `findExerciseByName()` in `features/exercises/utils/exercise_match.dart`; the AI function's `Catalog`). Never match exercise names with a bare `toLowerCase()`.
- **Percentage sets on another user's workout resolve against the *viewer's* 1RM.** `CommunityWorkoutDetailScreen` is a preview of "what would this session cost me", not a transcript of what it cost its author — the resolved weight renders in `NomorexTokens.info` (blue), absolute-weight sets stay default-colored because they're the same load for everyone, and a set with no resolvable 1RM offers the `SetPrLink` shortcut instead. `WorkoutDetailScreen` also renders other users' public workouts and follows the same rules.
- **Adding sets uses stepper inputs, not free text.** `SetEditor` (`lib/features/workouts/widgets/set_editor.dart`) uses the shared `NumberStepperField` (`lib/shared/widgets/number_stepper_field.dart`, tap +/- or type directly, floored at a sensible minimum) for sets/reps/percentage/weight — there's no shorthand grammar to parse. The percentage dialog has a single %1RM stepper shared by every set in the batch, like the weight dialog, so it stays a fixed height — wave-loading (a different percentage per set) means adding another batch. Both dialogs are one "Add sets" sheet (bottom sheet on a phone, centered panel wider) that reads the batch back as a sentence ("3 × 8–10 @ 70–75%" plus the resolved load) above the fields. Reps and %1RM each have a ONE | RANGE toggle (announced as switches "Rep range", "%1RM range") that adds a second stepper, built from the shared `_RangeInput`; a range narrowed to one number is saved as a single value (the `*_max` column stays null). `ParsedSet` (`lib/features/workouts/utils/parsed_set.dart`) is the reps+percentage DTO (with optional range tops) passed to `WorkoutDetailNotifier.addPercentageSets`. The weight dialog collects sets/reps/weight together and calls `addAbsoluteSets`, converting from the display unit to kg first.
- **RPE is a target on the set and, separately, a logged result.** `rpe_min`/`rpe_max` (1–10, half steps; `rpe_max` null = a single RPE) are prescription columns on both `workout_sets` and `program_sets`, set from the "Add target RPE" control in both `SetEditor` sheets and shown as "RPE 6–7" via `formatRpeTarget()` (`core/utils/rpe.dart`). `workout_sets.actual_rpe` is logging-only, like `actual_reps`: written by `WorkoutDetailNotifier.logSet` from the live row's "Log set" sheet (`showLogSetSheet`, behind `LogSetChip` on a live (`in_progress`/`paused`) session), shown read-only afterwards, never pre-filled from the target, and never copied by `copy_workout_tree`/`copy_workout`.
- **Every set is a warm-up, working set or cool-down** (`set_type` on `workout_sets` and `program_sets`, #145). It's text checked `in ('warmup','working','cooldown')` with default `'working'`, read through `SetType.fromDb()` (`lib/shared/models/set_type.dart`), which reads an unknown value as working so a type added on the server later doesn't break an older app. **An exercise's "2/4 sets" count and the program editor's summaries cover working sets only** (`countedSets()`: an exercise with no working sets counts them all, so it's never "0/0"); warm-ups and cool-downs are listed after ("4 × 3 · 100 kg · 2 warm-up") and never widen the load. It's a prescription column, so it's in `groupConsecutiveSets`'s comparison (a warm-up never joins working sets), `SetsSheetInitial` and the group prescription map, and every copy RPC carries it (`20261116015735_add_set_type.sql` is the newest definition of `copy_workout_tree`, `copy_workout` and `replace_program_set_group`, which falls back to `'working'` when the prescription omits it; `start_program`, `copy_program` and `_copy_program_day_contents` were redefined since, see Database). Type is chosen per batch in both "Add sets" sheets (Working preselected) and changed per group from `SetEditor`'s ⋯ menu ("Mark as warm-up set"), which rewrites the group through `onReplaceGroup`. Read-only set lists (workout, Community workout, program day) show the type as a header above each run of one type (`withSetTypeHeaders()` in `lib/shared/widgets/set_type_header.dart`; none when every set is working), never inside a row, so every row's reps line up. **A type keeps its run in place: warm-ups, then working sets, then cool-downs.** New sets go to the end of their type's run (`placeByType()` in `set_type.dart`, called by both detail notifiers' add methods after the insert), and retyping a group in the editor moves it to the new type's run before rewriting it; within a type the order is the lifter's (drag, or Move up/down). AI import doesn't detect types yet; imported sets get the default.
- **A live set reads reps × load, and logging is one sheet** (#148). `SetPrescriptionLines` (`lib/features/workouts/widgets/live_set_row.dart`) is the shared row for the workout screen and Community: a main line "3 × 165 lbs / 75 kg" (reps in `stat`, the load in `weightLg`, `info` blue when resolved from a %1RM) over the prescription in body-small ("75% of 1RM · RPE 8"; "No 1RM yet · set PR" with the `SetPrLink`; open load "3 × choose load"). On the workout screen the checkbox is its `leading` (ticking marks the set done as prescribed) and `LogSetChip` its `trailing` ("Log", then "3/3 · RPE 7"), which opens `showLogSetSheet`: reps, RPE behind "Add RPE", and weight on an open-load set. Saving calls `logSet(..., complete: true)` in one update; "Clear log" empties the logged values and leaves the done state. The chip sits under the main line on a phone and ends it from 520px. Prescription and result stay separate: the main line never shows logged values.
- **The editors edit groups of identical sets** (#148). `SetEditor` (workout editor and the desktop program editor) shows one row per run of identical consecutive sets (`groupEditableSets`: every prescription column, the note and the type count), under a run header per type, each type its own `ReorderableListView` so groups drag within their type. Tapping a row reopens the sets sheet filled in (`SetsSheetInitial`) and saves the whole group through `onReplaceGroup`, which callers wire to `replace_workout_set_group` / `replace_program_set_group`; its ⋯ menu (`showActionSheet`, now in `lib/shared/widgets/action_sheet.dart`) edits the last set only, retypes, moves up/down (the keyboard path), or removes, asking first for more than one set. The sets sheet waits for the save (`_submitSheet`: a spinner, and a failure stays in the sheet with everything still entered); removing a group shows an Undo snackbar that re-adds it, puts it back in place and restores its note; other failures show a snackbar. A percentage group with no 1RM says "No 1RM yet · set PR" (`SetPrLink`, outside the row's button). The editor list sits in `contentPadding()`, like the fields above it. The phone program editor's `SetGroupEditor` works the same way on `ProgramSet`s.
- **The privacy policy is `web/privacy.html`.** It's a static page that the web build copies through, published on GitHub Pages at `AppConstants.privacyPolicyUrl`, which Profile's "Privacy policy" link opens through `externalLinkOpenerProvider` (`core/utils/external_link.dart`). The same URL is entered in App Store Connect and Play Console, so it mustn't move. Its `#delete-account` section is the account-deletion page Google Play requires. **A change to what the app collects, shows to other users or sends to a third party** (a new personal-data column, the Sentry user context in `sentryUserSync`, a new service provider, the AI import notice) **updates the policy, `ios/Runner/PrivacyInfo.xcprivacy` and the store data-disclosure answers in the same PR.** `test/privacy_policy_test.dart` fails while any `class="todo"` placeholder is left in it.
- **Exercises are official or custom.** Official rows (`is_predefined = true`, "predefined" in older code) are visible to everyone; custom ones are scoped by `user_id`. The list query is `.or('is_predefined.eq.true,user_id.eq.$userId')`. Only official rows have a `slug` (permanent, `clean_and_jerk`), `aliases` (other names, "C&J") or `retired_at`; a check constraint keeps custom rows bare. Clients can't write official rows; the `exercises_before_write` trigger tidies names, keeps slugs permanent, and refuses a name or alias another *active* official exercise already answers to (`20261114202746_official_exercise_catalog.sql`).
- **Official exercises are removed by retiring, not deleting.** A retired exercise (`retired_at` set) is hidden from both pickers (`ExercisePickerPanel`, `ExercisePicker`) but stays in `exercisesProvider` and keeps matching by name, because PRs, logged workouts, programs and percentage bases still point at it. Every foreign key to `exercises` refuses the delete (the `basis_exercise_id` ones were `SET NULL`, which silently re-pointed "75% of C&J" sets at their own lift), so a hard delete only works for an exercise nobody uses.
- **The official catalog lives in the database and in `supabase/catalog/official_exercises.sql`.** That file is a slug-keyed upsert that can be replayed any number of times: `supabase db reset` loads it before `seed.sql` (`[db.seed] sql_paths`), and after wiping a hosted project it's pasted into the SQL editor once to bring the catalog back. It updates or creates, never deletes. The catalog is edited in the app, at **Profile → Admin → Exercises** (`AdminExercisesScreen`): add, rename, set other names, retire/restore, and delete one nobody uses. Its **Export catalog** button returns the file's exact contents (`admin_export_exercises()`, rows sorted by slug, so a diff shows only real changes); commit that over the file to keep it in step. Renaming in the edit dialog adds the old name to the other names where the admin can see it and remove it, so a typo fix doesn't keep the typo; the server function itself just saves what it's given. Never change a slug in it: that makes a second exercise instead of a rename. `seed.sql` refers to official exercises by name, so renaming one there means updating `seed.sql` too.
- **Tempo/pause/technique modifiers aren't separate exercises.** "Pause Front Squat," "Tempo Snatch Deadlift," etc. all log against the base lift (e.g. "Front Squat") with the modifier captured as a note on the `workout_exercise`/`program_exercise` row — this keeps 1RM/PB tracking coherent. A modifier only earns its own `exercises` row when a competent lifter would track a separate PR for it (e.g. Hang Power Clean vs. Power Clean).
- **Programs have no hard delete.** "Delete" in the UI archives (`programs.is_archived = true`, reversible via restore) rather than issuing a real `DELETE` — `program_instances.program_id` uses `ON DELETE RESTRICT` as a database-level backstop, but the app itself never exposes hard delete once a program has instance history.
- **Workouts archive; hard delete only from the archive.** Archiving sets `workouts.is_archived`/`archived_at` (`20261027023100_archive_workouts.sql`) and is reversible. `WorkoutsNotifier.archiveWorkout`/`restoreWorkout`/`deleteWorkoutPermanently` act on the **whole `workout_group_id`**, not one row, because one Workouts-list card stands for every session of a workout. Acting on just the representative would bring a sibling session up in its place. `deleteWorkoutPermanently` also filters on `is_archived = true`, so an active workout can't be hard-deleted even by a bug in the UI. It's only offered from the archived list on Training's Workouts view (`ArchivedRowActions`'s "Delete permanently"). Archive is hidden for a live (`in_progress`/`paused`) session and for program-materialized workouts (`canArchiveWorkout`). An archived workout leaves the Workouts list, Community (`copy_workout` raises `archived:`) and the copy-count hint, but **its finished sessions stay in history**: `finishedWorkoutsProvider` deliberately doesn't filter on it. Archived programs and workouts open read-only (no edit/start/repeat, just Restore). Repeating an archived session would add a live row to an archived group. Both lists switch to their archived items with `ArchivedToggle`, and archived rows use `SummaryCard(archived: true)`, as specified in the design system.
- **Community content is copied, never shared live.** Saving or starting another user's public workout/program calls `copy_workout` / `copy_program` (`20261013023308_add_content_copies.sql`), which build a private copy owned by the viewer in one transaction — exercises mapped into the viewer's catalog by name via `map_exercise_for_viewer`, logged results never copied, and for Start the copy is then run through the existing `start_workout_session` / `start_program`. A copy is marked `is_copy` **permanently** (a `BEFORE UPDATE` trigger rejects un-marking it) and can never be public (`CHECK (not (is_copy and is_public))`), so the Public switch is disabled on copies. Copy status must follow anything derived from a copy: `start_program` stamps it onto materialized workouts, and creating a workout from an existing one goes through `duplicate_workout`, `finish_workout` (the next instance) and `repeat_workout` (`20261111232702_workout_copy_rpcs.sql`), which copy the whole workout in one transaction and read attribution from the source row in `new_workout_from`, never from the client. **A new such path must be an RPC built on `new_workout_from`** rather than a client-side insert, or duplicating becomes a way to re-publish someone else's work. The author's name is a snapshot (`copied_from_display_name`) because `profiles_select` hides an author's profile once they stop sharing; render it through `CopiedFromBadge` / `copyAttributionLabel()`.

## Database

Schema is code under `supabase/migrations/`. Tables: `profiles`, `exercises`, `personal_bests`, `workouts`, `workout_exercises`, `workout_sets`, `programs`, `program_weeks`, `program_days`, `program_sessions`, `program_exercises`, `program_sets`, `program_instances`, and `ai_import_jobs`, `ai_import_results`, `ai_import_limits`, `ai_import_consents`, and `roles`, `user_roles`, `admin_audit_log`. `workout_exercises`, `workout_sets`, and all `program_*` tables carry a denormalized `user_id` so RLS can be enforced without joins — new inserts must populate it.

**AI import tables are written only through functions.** Users have `SELECT` on their own `ai_import_jobs`/`ai_import_results` and no direct writes, so they can't edit the rows that enforce their own quota. `ai_import_start`, `_finish`, `_save_result`, `_claim`, `_mark_accepted` and `_discard` are the project's `SECURITY DEFINER` exception (justified on #79); each does one transition on the caller's own job, and anything new like them needs the same care: `search_path = ''`, an explicit `auth.uid()` ownership check, and `anon` revoked, since default privileges grant it every routine. `ai_import_jobs.provider` says which pipeline ran it: `hosted` (the `ai` function) or the app itself with the lifter's own key (`anthropic`, `openai`, `gemini`) or on device (`on_device`), whose result the app stores through `ai_import_save_result` (`20261126021010_ai_import_save_result.sql`, #184) as a `ready` job that reviews and accepts like any other. Only `hosted` runs count toward the caps (`ai_import_check()` filters on it, and a constraint keeps `counts_toward_limits` false on the rest), and saving needs no notice, files or the imports switch; it caps unreviewed results at 20 instead. One `ai_import_jobs` row is one AI run, so a re-run adds a row and marks the old one `replaced`; never delete rows to tidy up, because the caps count them. Whether a failure counts is decided inside `ai_import_finish` from its code, not by the caller. Limits and the off switch are the single row in `ai_import_limits`. It ships with `enabled = false`; `seed.sql` turns it on for local and CI stacks. `ai_import_accept` saves a reviewed import in one transaction, `SECURITY INVOKER` apart from the claim and mark-accepted helpers. Its payload is the stored result with each absolute load as `weightKg`, converted by the client; a raw `weight` is refused by the set constraint rather than saved in the wrong unit. Imports are `is_copy = true` for privacy, plus `is_imported` for the "Imported" label, so anything that derives a workout must carry both (`start_program`, `new_workout_from`). Files live in the private `ai-imports` bucket at `{user_id}/{import_id}/{file}`, and its upload policy also requires the notice to be accepted and `ai_import_check()` to allow a start. The app side is `AiImportIntakeNotifier` (`lib/features/ai/providers/ai_import_intake_provider.dart`): it refuses files over the limits before upload (up to `max_images` images, or PDFs whose pages add up to at most `max_pdf_pages`, never a mix; the page cap is per import, not per file, because the output budget is), uploads them as `page-N.<ext>` in the order shown, PDFs sorted by file name in natural order as they're picked, because the flow reads files in natural name order and labels them "Page N:" (images) or "File N:" (PDFs), then calls `startAiImport`. Any failure before the start deletes what was uploaded; a start whose outcome is unknown (`NETWORK`/`UNKNOWN`) leaves the files, since the import may be reading them. `prepareImportImage` downscales to 2576 px on the long edge (Claude's limit), turns photos upright and strips EXIF so a photo's location is never uploaded. The picker does most of that on iOS, Android and web; the Dart fallback covers desktop. Its client checks are only for the user's benefit, so a new rule that matters must also be enforced on the server. The way in is `kAiImportAction` (`lib/features/shell/nav_section.dart`), the last entry in both "New" menus: the sidebar's and the phone's + sheet, shown while `aiImportAvailableProvider` is true (see "Bring your own AI"). **The hosted path's off switch is Profile → Admin → AI imports** (`admin_set_ai_imports_enabled`, which writes an audit row), with `update public.ai_import_limits set enabled = false;` (and `true`) in the SQL editor as the fallback. It makes the server refuse every hosted start; an import already running still finishes. Since #188 it no longer hides the entry points while a key can be stored: lifters without one are offered the AI assistant settings instead. The import screen checks `ai_import_check()` as it opens (`aiImportGateProvider`). `consent_required` shows the one-time notice, which names Anthropic and, when accepted, inserts the user's `ai_import_consents` row; "Not now" leaves without recording or uploading anything. Any other refusal (switched off, an import already running, a cap reached) shows `importCheckMessage()` instead of the file pickers. Change the notice's wording together with the privacy policy (`web/privacy.html`) and the store data-disclosure answers, which describe the same thing. Job status reaches the app through `aiImportJobsProvider` (`ai_import_jobs_provider.dart`), the only source of truth: Realtime and app resume only prompt a re-read, because events missed while disconnected aren't replayed. `aiImportJobWatchProvider` subscribes to Realtime **only while a job is processing** (and re-reads on every (re)subscribe), so users who never import never hold a socket open; a job started on another device while this one is open shows up on the next resume or Home refresh. A job still `processing` past `max_job_seconds` is shown as failed (`AiImportJob.state`) without waiting for the sweep. `AiImportJobAlerts`, wrapped around the app in `MaterialApp.router`'s `builder`, re-reads on resume and shows one snackbar per job that finishes (`ImportAlertTracker`: jobs already finished at launch are the baseline and don't alert). It sets `persist: false`, because a snackbar with an action otherwise never times out, and floats just above the phone's bottom bar. Home's Review button closes that job's alert through `importAlertSnackBarsProvider`. It sits above the `Router`, so it navigates through a callback rather than `context.push`. Anything that changes a job's status from the app (accept, discard, start) must `ref.invalidate(aiImportJobsProvider)`. The review (`AiImportReviewScreen`, `/ai-import/review/:jobId`) never edits the stored result in place: it parses it for display (`AiImportResult`) and applies the user's fixes to a copy with `buildReviewedPayload()` (`models/ai_import_result.dart`) when they accept. That's where each absolute load becomes `weightKg`, in its printed unit or else the kg/lb the user chose, and where an exercise fix is applied to every exercise and basis lift of that name. A custom exercise chosen in review isn't created until accept, so a discarded import leaves none behind. Re-run as the other type calls `startAiImport` again with the same `import_id`, which needs the uploaded files still in place.

**Admin roles are written only through functions** (`20261111214805_add_admin_roles.sql`). A role is a row in `roles` (a new role is an insert, not a type change), held through `user_roles`; neither is on `profiles`, whose "update own profile" policy would let anyone grant themselves a role. Clients can only `SELECT` (their own role rows, or everything for an admin). `admin_grant_role`, `admin_revoke_role`, `admin_set_ai_imports_enabled`, `admin_list_users` (which reads emails from `auth.users`), `admin_list_audit_log`, and the exercise catalog's `admin_list_exercises`, `admin_create_exercise`, `admin_update_exercise`, `admin_set_exercise_retired`, `admin_delete_exercise` and `admin_export_exercises` (`20261114212947_admin_exercises.sql`, tested in `admin_exercises.test.sql`) are the second `SECURITY DEFINER` family: each starts with `require_role('admin')`, which isn't callable by clients, and each change writes one `admin_audit_log` row (a no-op change writes none). Role changes take `lock_user_roles()` before the role check so they run one at a time, and an admin can't revoke their own role, which together keep at least one admin. A new admin function follows the same shape: the role check first, an audit row for every change, `search_path = ''`, `anon` revoked, and a case in `admin.test.sql`. The first admin of a hosted project is created by hand (`docs/build.md`, "Admins"); `seed.sql` makes `a@a.com` the local admin.

**Set values are bounded in the database, not only by the steppers** (`20261111015854_reject_invalid_set_values.sql`): reps ≥ 1, %1RM above 0 and at most 200 (`kMinSetPercentage`/`kMaxSetPercentage` in `core/utils/percent_range.dart`, the same bounds `ai_import/normalize.ts` accepts), loads and logged weights ≥ 0, logged reps ≥ 0; `personal_bests` needs reps ≥ 1 and weight > 0. Change a stepper's floor or ceiling and the matching constraint together, or the app offers a value that fails to save with a raw Postgres error. `set_value_bounds.test.sql` covers them.

Any new table in `public` **must** enable RLS and add ownership policies `TO authenticated using ((select auth.uid()) = user_id)`, with UPDATE declaring both `USING` and `WITH CHECK`. `supabase db lint` runs in CI.

**Database tests are pgTAP files in `supabase/tests/database/*.test.sql`**, run by `supabase test db --local` (in `verify.sh` and CI's `db-validate`, after a reset, so the seeded users exist). They're the only tests that exercise the server-side functions and constraints. Widget tests never reach the database. `set_prescription_copies.test.sql` is the pattern: insert fixtures as superuser, then `set local role authenticated` plus a `request.jwt.claims` sub to act as a seeded user, and wrap everything in `begin … rollback`. **Any change to `start_program`, `copy_program`, `copy_workout`, `duplicate_workout`/`finish_workout`/`repeat_workout` (tested in `workout_copy_rpcs.test.sql`) or a `workout_sets`/`program_sets` constraint should add or update a test there.** RLS itself is covered by `rls_ownership.test.sql` (b@b.com against a@a.com's private rows in every user-owned table), `rls_visibility.test.sql` (what public content, exercises and profiles another user or `anon` can see) and `rls_rpcs.test.sql` (functions refuse another user's content; copy rules); **a new user-owned table or policy should add a case to them.** Child policies check only `user_id`; that a child's parent (workout, program, week, day, exercise, program run) has the **same owner** is enforced by `check_parent_owner()` triggers (`20261111022449_child_rows_require_owned_parent.sql`), which a new child table or parent link needs too. They're `AFTER ROW` triggers rather than an `EXISTS` in the policy because a policy can't see parent rows inserted earlier in the same statement, which is how `copy_program`/`start_program` build a tree. `.claude/settings.json` denies `--linked`/`--db-url` on every `supabase` command, so these can't be pointed at a hosted project by accident.

**Programs schema.** `programs -> program_weeks -> program_days -> program_sessions -> program_exercises -> program_sets` mirrors `workouts -> workout_exercises -> workout_sets` one level deeper (`program_sets` has no `completed`/`actual_*` columns — those stay logging-only on `workout_sets`). `program_days.position` is the day's *global* order across the whole program (not just its week) and drives drag-reorder; its value doesn't set a date. **A day's date is `start + 7 × week index + its place in the week`** (both 0-based, by position; `20261120061847_limit_program_weeks_to_seven_days.sql`), so every week takes 7 calendar days however many it holds, and an empty week is a week off. The client mirrors this as `ProgramDay.dayOffset` (set in `Program.fromJson`, `StatsWeek.fromJson` for a run's structure), which is what `programDayDate()`, `isProgramDayToday()` and the run stats take; never date a day from `position`. A week holds at most 7 days: the `enforce_program_week_day_limit` trigger refuses an 8th on every path (editor, copy RPCs, `copy_program`, AI import). `day_number` is the day's place in its week (Day 1–7), display-only and not unique. `workouts.program_instance_id` / `workouts.program_day_id` / `workouts.program_session_id` (all nullable, `ON DELETE SET NULL`) link a materialized workout back to the program run that generated it, without making logged history depend on the template surviving. **A day's sessions** (`program_sessions`, `20261122042254_program_day_sessions.sql`) hold its exercises: `title`/`notes` optional, `position` unique per day, at most 3 (`enforce_program_day_session_limit`). `program_exercises` keeps `program_day_id` as a denormalized copy of its session's day, kept in step by triggers (`program_exercises_fill_session` fills whichever is missing, so an older client inserting by day lands in the day's first session; `check_program_exercise_session_day` refuses a session from another day). Every function that creates a day creates its session; a day with none is tolerated (it materializes one empty workout). `start_program` makes one workout per session on the day's date, titled "<day> · <session or Session N>" when there are several, with the day's notes then the session's.

**`start_program(p_program_id, p_start_date)`** (in `20260805020858_create_start_program_function.sql`) is the first non-trivial server-side `plpgsql` function in this codebase beyond the existing trigger functions (`handle_new_user`, `set_updated_at`). It's `SECURITY INVOKER` (not `DEFINER`) so it stays gated by the same RLS a direct client insert would hit, and does the whole weeks→days→exercises→sets walk in one transaction — this is why "Start Program" is an RPC call rather than a client-side loop: a multi-week program is large enough (dozens of workouts, hundreds of exercises/sets) that a sequential client-side version would be slow and have no rollback on partial failure. Every `program_day` materializes a `workouts` row per session, including empty rest days.

`start_program` has since been replaced several times (signature unchanged) to stamp copy attribution (`is_copy`, `is_imported`, `copied_from_*`) and the day's notes onto each workout it materializes; `copy_program` builds on it. Any further change to `start_program` must start from its newest definition, currently `20261122042254_program_day_sessions.sql`, not the original file. That migration is also the newest definition of `copy_program`, `_copy_program_day_contents`, `add_program_week`, `add_program_day`, `ai_import_create_program`, `ai_import_create_workout` and `ai_import_place_notes`.

**The program editor's bulk edits are RPCs** (`20261113204234_program_editor_rpcs.sql`, #126): `duplicate_program_week` (inserts the copy right after the week), `copy_program_day(day, weeks[])` (appends to each target week; the day's own week is Duplicate day) and `replace_program_set_group(set_ids, count, prescription jsonb)` (rewrites a run of identical consecutive sets in place; count 0 removes it). `reorder_program_weeks(program, week_ids[])` (`20261113212831_reorder_program_weeks.sql`) is what `reorderWeeks` calls: moving a week has to move its days' global `position`s too, because the global day order has to follow the weeks for the other RPCs' placement, so never renumber weeks alone from the client. `add_program_week` (a week of 7 rest days, Day 1–7) and `add_program_day` (one day at the end of a week with room) are what `addWeek`/`addDay` call (`20261120061847_limit_program_weeks_to_seven_days.sql`, tested in `program_week_day_limit.test.sql`). They renumber `week_number` and the global day `position` through negatives, the same trick as `reorderWeeks`/`reorderDays`, because both are unique per program. All `SECURITY INVOKER` and refuse anything not the caller's own, including a public program's rows; copying another user's content still goes only through `copy_program`. Every prescription column is copied, so a new `program_sets`/`program_exercises`/`program_sessions`/`program_days` column must be added to `_copy_program_session_contents`/`_copy_program_day_contents` and `replace_program_set_group` as well as `copy_program`. Sessions have their own RPCs, `add_program_session`, `duplicate_program_session` and `reorder_program_sessions` (`20261122042254_program_day_sessions.sql`, tested in `program_sessions.test.sql`). Tested in `program_editor_rpcs.test.sql` and `rls_rpcs.test.sql`. **`replace_workout_set_group(set_ids, count, prescription jsonb)`** (`20261116034616_add_replace_workout_set_group.sql`, #151) is the workout counterpart, for the workout editor's set groups: the same refusals and shift, every prescription column plus `set_type` (default `'working'`), and the new rows get the logging columns' defaults (the editor is only offered before a session starts). A new `workout_sets` prescription column must be added to it too. Tested in `workout_set_group_rpc.test.sql` and `rls_rpcs.test.sql`.

**Never add a second foreign key between two tables the app already embeds through PostgREST.** `workouts` and `programs` each have a `user_id` FK to `profiles`, and the app embeds `profiles(display_name)` on them; a second FK to `profiles` makes PostgREST reject every such embed as ambiguous (`PGRST201`). Because migrations deploy ahead of app code, that breaks the app version already deployed the moment the migration lands. This is why `copied_from_user_id` references `auth.users` (not exposed through PostgREST) instead of `profiles`. Widget tests can't catch this (they never hit the database) — check any new FK against the app's embedded selects on a local stack.

**Position/sequence fields must be derived from `max(existing) + 1`, not a count.** `ProgramDetailNotifier.addWeek`/`addDay` (`lib/features/programs/providers/program_detail_provider.dart`, now the `add_program_week`/`add_program_day` RPCs) used to compute the next `week_number`/`position` from `weeks.length`/`totalDays`. Deleting a week or day from the middle of a program left the count behind the highest number still in use, so the next insert collided with a surviving row and threw on the `program_weeks_program_id_week_number_key` / `program_days` position unique constraint — fixed by deriving from `max(existing) + 1` instead. The same "position = count" shape still exists in `add_program_day`'s `day_number` (harmless — `day_number` is intentionally not unique) and `addExercise`'s `position: day.exercises.length` (`program_exercises.position` has no unique constraint either, so it won't crash, but can still produce silently wrong ordering after a mid-list delete). Treat any new `position`/`order` assignment in this codebase with the same suspicion.

## CI/CD

**Tool versions are pinned once, in composite actions:** `.github/actions/setup-flutter`, `setup-supabase` and `setup-deno` wrap the upstream setup actions with the pinned version, and every workflow calls them (after `actions/checkout`, since a local action needs the repo). Bump a version in that one file; `scripts/lib/cloud.sh` (`read_pins`) and `scripts/verify.sh` read the same lines, so keep the `flutter-version:` / `version:` / `deno-version:` key and format. Don't pin a version inline in a workflow.

- `.github/workflows/pr-checks.yml` — six parallel job definitions, no `needs:` between them: `checks` (`./scripts/check-generated.sh`, `flutter analyze`, `flutter test`), `build-web` (matrix over `release`/`debug`/`profile`), `build-android` (APKs: every mode as the `local` flavor, plus a release build of `beta` and `production`), `build-ios` (`flutter build ios --release --no-codesign --flavor <local|beta|production>` on `macos-26`, one job per flavor), `db-validate` (`supabase db reset` + `db lint` + `test db`), and `e2e` (see E2E tests below). Both build matrices use `fail-fast: false` so one broken mode doesn't hide the others; release APKs are signed with the debug keys, so no signing secrets are needed. The builds are deliberately separate from `checks` — the Gradle build dominated it and was delaying analyze/test feedback. Only `build-android` sets up Java; the other jobs don't need it.
- `.github/workflows/self-hosted-test.yml` — runs every 4 hours on a schedule (`0 */4 * * *`, UTC, against `main` only, since scheduled runs always use the default branch) and on demand via `workflow_dispatch`, on the self-hosted `arc-runner-set`: a `test` job (analyze + tests + coverage) and a `build-web` matrix (`release`/`debug`/`profile`) in parallel. Its Flutter version comes from the shared `setup-flutter` action, like every other workflow.
- `.github/workflows/deploy.yml` — on push to `main`, builds and publishes the web app to GitHub Pages (with `--base-href` set to the repo subpath).
- `.github/workflows/deploy-ios.yml` — on push to `main` (its own `paths-ignore`, which keeps `ios/**`), archives a signed release build of the **beta** flavor (scheme `beta`, configuration `Release-beta`) on `macos-26` and uploads it to TestFlight under the `com.nomorex.app.beta` record; the original `com.nomorex.app` record is reserved for production. Signing is cloud-managed through an App Store Connect API key (`APP_STORE_CONNECT_KEY_ID`/`_ISSUER_ID`/`_API_KEY_P8` secrets) and `-allowProvisioningUpdates`, so no certificate or profile is stored. `ios/ExportOptions.plist` has `destination=upload`, so the export step is also the upload. It uses `flutter build ios --config-only` + raw `xcodebuild` because `flutter build ipa` can't pass the API-key flags. Version comes from `version.yml`, the same as the web deploy. Setup checklist: `docs/build.md`.
- `.github/workflows/deploy-functions.yml` — on push to `main` touching `supabase/functions/ai/**`, deploys the `ai` edge function with the CLI (needs the `SUPABASE_ACCESS_TOKEN` secret), then checks that a request with no session gets a 401. Its CLI version comes from the shared `setup-supabase` action.
- `.github/workflows/ai-import-cleanup.yml` — daily at 09:17 UTC, and on demand, POSTs to the `ai-import-cleanup` function with the `AI_IMPORT_CLEANUP_SECRET` secret from the `beta` GitHub Environment (the job declares `environment: beta`; a job only sees an environment's secrets when it names it). The same value must be set as the function secret on that environment's Supabase project (a different value per project). The job reads the project from the `SUPABASE_URL` variable of the same GitHub Environment, so it needs no project ref in the YAML. The run fails on anything but 200, including partial failures, so problems show up in Actions.
- Migrations are deployed **separately**, by the Supabase GitHub integration watching `supabase/`. The integration is linked to one project (beta today); a production project needs its own link and its own function secrets. The two are unordered relative to each other, so ship additive migrations ahead of the code that depends on them. **Relaxed until the public launch:** the hosted database will be wiped before launch, so for now a breaking migration (dropping or reshaping a column, tightening a constraint) may land in the same PR as the code that needs it, with no compatibility step for the app version already deployed. The migration must still apply cleanly to the hosted project's existing data, or every later migration is blocked behind it. When the launch wipe happens, delete this paragraph and go back to additive-first.

## Testing

Widget tests stub data by **subclassing the generated notifier and overriding `build()`**, then passing it to `ProviderScope(overrides: [...])` — e.g. `workoutsProvider.overrideWith(() => _EmptyWorkoutsNotifier())`. Simple derived providers use `overrideWithValue` (`unitPreferenceProvider.overrideWithValue('kg')`). There is no Supabase mock; tests never hit the network. Pure logic (parsers, resolvers, model JSON) is tested directly without widgets.

### E2E tests (`integration_test/`)

`flutter test` only runs `test/`; the E2E suite is separate and always goes through its runner:

```bash
./scripts/e2e.sh          # macOS desktop (default), stack as it is
./scripts/e2e.sh linux    # Linux desktop, how CI runs it
./scripts/e2e.sh --reset  # `supabase db reset` first (local only, never --linked)
./scripts/e2e.sh --file integration_test/app_test.dart   # one file, for debugging
```

The script starts the local stack and runs `integration_test/all_tests.dart`, which calls every file's `main()`, so the app is **built and launched once** for the whole suite. It only resets the database with `--reset` (CI and `verify.sh` pass it; locally a reset wipes your own test data, so it's opt-in). Unlike widget tests, these boot the **real app against real Supabase**: no provider is stubbed. That's forced by `RouterNotifier.redirect` in `lib/app.dart`, which reads `Supabase.instance.client.auth.currentSession` directly rather than through a provider, so it can't be overridden — anything past `/` needs a genuine session. Tests sign in as the seeded **`e2e@e2e.com` / `123456`**, an account only this suite uses, so a run never touches `a@a.com`'s data. A stack seeded before that user existed needs one `--reset` (the script says so). Locally the script passes the same `.env.local.json` used for a normal run; in CI, where that gitignored file doesn't exist, it instead reads `API_URL`/`PUBLISHABLE_KEY` straight off the running stack via `supabase status -o env`.

Rules for adding to the suite:

- **A new `*_test.dart` goes in `integration_test/all_tests.dart`** (import with a prefix, call its `main()`); `scripts/e2e.sh` refuses to run while one is missing. **Never call `flutter test integration_test` on the whole directory:** each file would launch its own app window, and a second launch fails with `Unable to start the app on the device`. `all_tests.dart` is the way to run several files in one launch.
- **Go through a page object** in `integration_test/support/pages/`, never raw finders in a test body.
- **Target keys, not text**, for anything you interact with — add a `Key('screen_thing')` to the widget in `lib/` as needed. Nav tabs and bottom-sheet entries are the exception; their labels are unambiguous.
- **Use `waitFor` / `waitForAbsent` from `support/harness.dart`** after anything that hits the network. A bare `pumpAndSettle` blocks on the spinner that's still on screen and reports a far less useful failure.
- **Assert presence, not counts.** The suite must stay green re-run against a stack that wasn't freshly reset. The converse doesn't hold: it writes to the database (saved copies, a PR), and the pgTAP tests assume a freshly seeded one (`admin_exercises.test.sql` and `exercise_catalog.test.sql` count custom "Dude Pulls" rows), so run `supabase db reset` before `supabase test db` on a stack the E2E suite has used. CI and `verify.sh` reset first.
- The harness initializes Supabase with `EmptyLocalStorage` so sessions never persist to disk. Don't remove that: with the default storage, a session from a previous run is restored *asynchronously* during `initialize` and races the sign-out, which makes only the first test of a run fail.
- **The harness pins every test to a 1280×800 viewport** (`_pinViewport`), so the window the OS happens to give the app (xvfb, a saved macOS frame) can't change the layout. Below 600px there is no sidebar. Don't `find.text` something at the bottom of a scrolling screen: a `ListView` only builds children near the viewport, so a taller layout can make it vanish. Wait on something at the top or give the widget a `Key` and `ensureVisible`. `bootSignedIn` signs in through the auth API; only `app_test.dart`'s first test goes through the landing and login screens.
- Both desktop targets are wider than the 600px `kMobileBreakpoint`, so these exercise the sidebar (`ShellPage` taps its destinations and its "New" menu, and `AiImportPage` reaches import through that menu). The mobile `BottomAppBar` branch stays widget-test territory.

**Widget tests render in `flutter_test`'s default ~800x600 surface.** A screen taller than that (nested `ExpansionTile`s, long lists) can push a target below the visible area — `tester.tap(finder)` on an off-screen widget doesn't throw, it just misses (a "hit test warning" that's easy to miss in the output), and the real failure surfaces later as something confusing and unrelated-looking, e.g. `Bad state: No element` from `enterText`/`showKeyboard` because a dialog never actually opened. Call `await tester.ensureVisible(finder); await tester.pumpAndSettle();` before tapping anything that might sit below the fold. After any UI change that adds height to a screen (more padding, more content), re-run the full suite rather than just the file touched — layout-adjacent tests can break invisibly.
