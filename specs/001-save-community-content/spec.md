# Feature Specification: Save and Start Community Workouts and Programs

**Feature Branch**: `001-save-community-content`

**Created**: 2026-10-12

**Status**: Draft

**Input**: User description: "A user can create their own programs or workouts and then have the ability to "start" those. Right now any programs or workouts in the community section are not able to be saved or started by the user. I need the user to be able to do this."

## Clarifications

### Session 2026-10-12

- Q: When someone taps "Start" on a community workout or program, should that also save a permanent copy to their own library? → A: Yes — starting always saves a visible copy to the user's library first, then starts it; the copy must be marked as a copy and name the original author.
- Q: Should a user be allowed to make their copy of someone else's workout or program public, so it shows up in Community again? → A: No — copies can never be made public; only content a user created themselves can be shared (for now).
- Q: When a user makes something new from a copy (duplicate, repeat, or workouts generated by starting a copied program), should the new item also count as a copy? → A: Yes — anything derived from a copy is also a copy: it credits the original author and cannot be shared.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Save a community workout and train it (Priority: P1)

A lifter browsing the Community tab finds a workout another user shared. Today they can only
look at it. They tap **Save to my workouts**, and a copy of that workout — every exercise, set,
rep target, load or percentage, and exercise note — appears in their own Workouts list. From
there it behaves exactly like a workout they built themselves: they can start it, log it, edit
it, or delete it.

**Why this priority**: a single workout is the smallest, most common unit of sharing and the
fastest path to value; it also proves out the copy behavior (exercise matching, percentage
basis, attribution) that programs reuse.

**Independent Test**: sign in as user B, open a public workout owned by user A from Community,
save it, then open it from B's Workouts list and start a session — B can log every set, and A's
original is unchanged.

**Acceptance Scenarios**:

1. **Given** a viewer looking at another user's public workout, **When** they choose "Save to my
   workouts", **Then** a new workout owned by the viewer appears in their Workouts list with the
   same title, exercises in the same order, the same sets, and the same exercise notes.
2. **Given** a saved copy, **When** the viewer opens it, **Then** it is editable and startable like
   any of their own workouts, and shows that it was saved from the original author.
3. **Given** a set in the original programmed as a percentage of a 1RM, **When** the copy is
   viewed, **Then** the percentage resolves against the **viewer's** 1RM for the same lift, and
   shows the "no 1RM" state if the viewer has none.
4. **Given** the save succeeded, **When** the viewer is still on the community screen, **Then**
   they get a confirmation with a way to go straight to the saved copy.
5. **Given** a saved copy, **When** the original author edits, unpublishes, or deletes the
   original, **Then** the viewer's copy is unaffected.

---

### User Story 2 - Start a community workout directly (Priority: P2)

A lifter wants to do a shared workout *right now*. From the community workout screen they tap
**Start workout**, which saves a copy (as in Story 1) and immediately opens it in an active
session, ready to log.

**Why this priority**: removes a step for the most common intent ("I want to do this today"),
but depends entirely on Story 1's copy.

**Independent Test**: as user B, tap Start on A's public workout and confirm B lands in an
in-progress session of B's own copy, and that the session appears in B's in-progress workouts.

**Acceptance Scenarios**:

1. **Given** a viewer on another user's public workout, **When** they choose "Start workout",
   **Then** a copy is saved to their workouts and they land in an in-progress session of that copy.
2. **Given** the start succeeded, **When** the viewer leaves and returns to the app, **Then** the
   session appears with their other in-progress workouts.

---

### User Story 3 - Save a community program (Priority: P2)

A lifter finds a multi-week program another user published. They tap **Save to my programs**
and a full copy — all weeks, days, exercises, sets and notes — appears in their own Programs
list, where they can edit it or start it like any program they authored.

**Why this priority**: programs are the higher-value shared content, but larger and
less frequently adopted than single workouts.

**Independent Test**: as user B, save A's public program, then open it from B's Programs list
and verify the structure matches and that B can edit it.

**Acceptance Scenarios**:

1. **Given** a viewer on another user's public program, **When** they choose "Save to my
   programs", **Then** a program owned by the viewer appears in their Programs list with the same
   name, weeks, days (including day order and rest days), exercises, sets, and notes.
2. **Given** a saved program copy, **When** the viewer opens it, **Then** they can edit it and it
   shows that it was saved from the original author.
3. **Given** the original program is later changed, archived or made private by its author,
   **When** the viewer opens their copy, **Then** it is unchanged.

---

### User Story 4 - Start a community program (Priority: P3)

A lifter wants to begin a shared program immediately. From the community program screen they
tap **Start program**, pick a start date, and the program is saved to their library and started
in one step — it then shows up under their current programs with its scheduled workouts, exactly
as if they had started a program they wrote.

**Why this priority**: convenience on top of Story 3; a user can already achieve the same
outcome by saving (Story 3) and then starting from their own Programs list.

**Independent Test**: as user B, start A's public program with a chosen date and confirm B
sees an active program run with one scheduled workout per program day, dated from the chosen
start date.

**Acceptance Scenarios**:

1. **Given** a viewer on another user's public program, **When** they choose "Start program" and
   a start date, **Then** a copy is saved to their programs and a run of that copy begins on the
   chosen date.
2. **Given** the run started, **When** the viewer opens their dashboard, **Then** the program
   appears in their current programs with today's day highlighted when applicable.
3. **Given** a failure partway through starting, **When** the operation ends, **Then** the viewer
   is left with neither a partial program copy nor a partial run, and sees an error they can
   retry.

---

### Edge Cases

- **Exercises the viewer doesn't have**: the original may use the author's custom exercises.
  The copy MUST map each exercise to the viewer's own exercise of the same name (case-insensitive),
  creating a custom exercise for the viewer only when they have none by that name. The same
  applies to a percentage set's 1RM basis exercise.
- **Duplicate exercise names in the viewer's catalog**: when the viewer has more than one
  exercise with the matching name, the copy uses the same one the app already picks when
  resolving that viewer's 1RM by name, so the copy and the 1RM lookup agree.
- **Saving the same item twice**: allowed — each save creates a separate copy. The screen
  indicates when the viewer already has a copy of this item so it isn't done by accident.
- **Viewing your own public item from Community**: Save/Start actions are not offered for
  content the viewer already owns; they use their normal screens instead.
- **Original becomes private or deleted while the viewer is looking at it**: the save fails with
  a clear message that the item is no longer available; nothing partial is created.
- **Program with empty / rest days**: rest days are preserved in the copy and in a started run.
- **Archived source program**: a program its author has archived no longer appears in
  Community and cannot be saved.
- **Logged results on the original workout**: the author's completion marks and actual
  weights/reps are never copied — the viewer's copy starts fresh.
- **Duplicating or repeating a copy**: the result is still a copy of the original author's work —
  credited and unshareable — so duplicating can't be used to get around the no-re-sharing rule.
- **Signed-out viewer**: Community content cannot be saved or started without signing in.

## Requirements *(mandatory)*

### Functional Requirements

**Saving**

- **FR-001**: Users MUST be able to save a copy of any public workout owned by another user into
  their own workouts.
- **FR-002**: Users MUST be able to save a copy of any public, non-archived program owned by
  another user into their own programs.
- **FR-003**: A saved copy MUST be owned solely by the saving user and MUST be fully editable,
  startable, and deletable/archivable by them under the same rules as content they created.
- **FR-004**: A saved workout copy MUST include the title, description, every exercise in its
  original order with its notes, and every set's position, target reps, weight mode, load or
  percentage, 1RM basis exercise, and set note.
- **FR-005**: A saved program copy MUST include the name, description, every week, every day
  (including rest days, day order, and day labels), and every exercise and set with the same
  detail as FR-004.
- **FR-006**: A saved copy MUST NOT include the author's logged results (completion status,
  actual weights/reps, session timing) or any of the author's program runs.
- **FR-007**: Exercises in a saved copy MUST reference the viewer's own exercise catalog,
  matched to the original by name, creating a custom exercise for the viewer only when no
  match exists. Shared (predefined) exercises are reused directly.
- **FR-008**: A saved copy MUST be private and MUST NOT be able to be made public, regardless of
  the original's visibility. The option to share MUST be unavailable on copies (with a short
  explanation), and the restriction MUST be enforced on the server, not only hidden in the UI.
  Copies therefore never appear in Community.
- **FR-008a**: Copy status MUST carry over to anything derived from a copy: duplicating or
  repeating a copied workout, and every workout generated by starting a copied program. Derived
  items MUST credit the same original author (FR-010) and MUST be unshareable (FR-008).
- **FR-009**: A saved copy MUST be independent of the original: later edits, unpublishing,
  archiving or deletion of either one MUST NOT affect the other.
- **FR-010**: Every saved copy — whether created by Save or by Start — MUST be visibly marked as a
  copy and name the original author, both on its entry in the user's Workouts/Programs list and
  on its detail screen. The marker MUST persist after the user edits or renames the copy, and
  MUST fall back to a neutral label ("Copied from another user") if the original or its author
  is later removed.
- **FR-011**: The save MUST be all-or-nothing — on failure, no partial copy remains — and the user
  MUST see an error message with the option to retry.
- **FR-012**: After a successful save, the user MUST see a confirmation with a direct way to open
  the copy.
- **FR-013**: Community detail screens MUST indicate when the viewer already has a saved copy of
  that item, while still allowing another save.

**Starting**

- **FR-014**: Users MUST be able to start another user's public workout from its community screen;
  this saves a visible copy to their Workouts list (FR-001, FR-010) and opens an in-progress
  session of that copy. There is no way to start a community workout without saving a copy.
- **FR-015**: Users MUST be able to start another user's public program from its community screen
  by choosing a start date; this saves a visible copy to their Programs list (FR-002, FR-010) and
  begins a run of that copy using the same scheduling behavior as starting their own program.
  There is no way to start a community program without saving a copy.
- **FR-016**: Start-from-community MUST be all-or-nothing across both the copy and the run/session.
- **FR-017**: Workouts generated by a started community program MUST behave identically to those
  generated by the user's own programs (where they appear, how they are logged, how progress is
  shown).

**Visibility & access**

- **FR-018**: Save and Start actions MUST NOT be offered on content the viewer owns.
- **FR-019**: Users MUST NOT be able to save or start content that is not public, or a program that
  is archived, even if they know its link.
- **FR-020**: Percentage-based sets in a saved copy MUST resolve against the saving user's own
  1RMs, consistent with how the community preview already shows them.

### Key Entities

- **Saved workout copy**: a regular workout owned by the viewer, plus a reference to the source
  workout and its author for attribution. No link to the source's logged results.
- **Saved program copy**: a regular program owned by the viewer (weeks → days → exercises → sets),
  plus a reference to the source program and its author for attribution.
- **Source attribution**: who the copy came from and which item; survives the source being made
  private or removed (falls back to "another user"), and is inherited by anything derived from
  the copy. Its presence is what makes an item a copy and therefore unshareable.
- **Exercise mapping**: the correspondence between each exercise in the source and the viewer's
  own same-named exercise, created on demand.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: A user can go from viewing a community workout to logging the first set of their
  own copy in 3 taps or fewer.
- **SC-002**: A user can go from viewing a community program to an active run of it in under
  30 seconds, including choosing a start date.
- **SC-003**: Saving a 12-week program with up to 6 days per week completes in under 5 seconds on
  a typical mobile connection.
- **SC-004**: 100% of saved copies match their source's structure (same count and order of
  weeks, days, exercises and sets) at the moment of saving.
- **SC-005**: 0 cases where a saved copy changes, or the original changes, as a result of the
  other being edited or removed.
- **SC-006**: 0 duplicate custom exercises created for a viewer who already has an exercise by
  that name.

## Assumptions

- "Start" for a workout means beginning a logging session immediately; for a program it means
  starting a dated run, as it does for the user's own programs today.
- Re-sharing copies is deliberately excluded for now; allowing it later (with author credit
  carried into Community) would be a separate feature.
- Copies are a one-time snapshot. Syncing later changes from the author is out of scope.
- Saving does not notify the original author and does not show save counts publicly (out of
  scope for this feature).
- Saved copies follow the same name-matching rule the app already uses to resolve a viewer's
  1RM for another user's exercises, so programmed percentages resolve consistently.
- A saved workout copy is dated the day it is saved and starts in the "not started" state,
  consistent with workouts the user creates manually.
- The existing Community browse and preview screens remain the entry points; no new discovery or
  search features are included.
