# ZT 6 Week Program

**Source:** Google Drive → Weightlifting → `ZT 6 Week Program` (shared by mkpenrod05@gmail.com)
**Files transcribed:**
- `6 weeks (1) Training.pdf` — Base Week 1/6
- `6 weeks (2) Training.pdf` — Loading Week 2/6
- `6 weeks (3) Training.pdf` — Loading Week II 3/6
- `6 weeks (4) Training.pdf` — Deload 4/6
- `6 weeks (5) Training.pdf` — Loading/Prep 5/6
- `6 weeks (6) Training.pdf` — Taper/Performance 6/6

**Length:** 6 weeks, Monday–Saturday (Sunday off, not listed). Classic base → load → deload → load → taper periodization.

## How to read the "Basis" tags

Percentage-based sets are tagged `[Basis: <Exercise> max]` for the lift the percentage is calculated from. Some sets reference "last week's" established load rather than a stored PB — these are tagged as session-to-session progressions, not true percentage-of-max sets.

## Notes / ambiguities for app design

- **RDL basis (Weeks 3–4)**: the source never names the reference lift for the plain "RDL" percentage sets. Assumed to be Clean-based given surrounding programming, but this should be confirmed — it's a good example of a case the app should probably force the program author to specify explicitly rather than infer.
- **Block Pull basis (Week 4 Saturday)**: same ambiguity — assumed Clean-based.
- **"Last week's ___" progressions**: several sets (Hang Power Snatch, Power Clean + Split Jerk, Heaving Hang Power Clean) are prescribed relative to a previous session's logged result rather than a percentage of a stored PB. This is distinct from the `resolveSetWeightKg()` percentage-of-1RM model described in CLAUDE.md and would need either manual entry each week or a "reference last logged set" feature.
- **RPE-based sets**: several days use RPE (e.g., Front Squat "build to RPE 8") instead of a percentage. These aren't percentage-of-max sets at all — they're a different set type the app may need to support alongside absolute and percentage modes.
